From Pull Request to Green Check

What actually happens behind the Jenkins status on your PR. ~25 minutes.

Your win today: trace a pull request in one of your repos all the way to the ✓ or ✗ that Jenkins puts on it, naming every piece involved. You'll understand what DevOps means by controller, agent, executor, queue, Jenkinsfile, multibranch and credential.

0. Warm-up: guess first

You don't know these yet, and that's the point. A guess now makes the answer stick later.

You open a PR, and a few seconds later a Jenkins check appears on it. How did Jenkins find out about the PR?

The Git host sends an HTTP message, called a webhook, to Jenkins the moment something happens. (Jenkins can also poll, checking the repo on a timer, but that's slower.) Section 3 covers this.

Where do the instructions "lint, then test, then deploy" usually live?

That file is the Jenkinsfile, usually at the root of your repo. It's the most useful thing in this lesson, and section 2 is about it.

1. Jenkins is a brain plus workers

Jenkins is an automation server. It runs a list of tasks for you whenever something happens (a push, a PR, a timer). It has two kinds of parts:

  • The controller is the brain: "the central, coordinating process which stores configuration, loads plugins, and renders the various user interfaces"jenkins.io, Glossary.. It's the website DevOps sends you links to. It also holds the build queue, the build history, and stored secrets.
  • Agents are the workers: "typically a machine, or container, which connects to a Jenkins controller". The real work (pytest, dbt run, a deploy script) runs on agents.
  • Each agent has executors: "a slot for execution of work". An agent with 2 executors can run 2 builds at once.
  • Agents carry labels, "user-defined text for grouping Agents, typically by similar functionality or capability", such as python or docker. A pipeline asks for a label, not a specific machine.

Why not run builds on the controller itself? The docs say running builds there "is discouraged for security, performance, and scalability reasons"jenkins.io, Managing Nodes.. The controller holds every secret, so you don't want arbitrary build code running next to them.

2. The Jenkinsfile: the pipeline lives in your repo

"The definition of a Jenkins Pipeline is written into a text file (called a Jenkinsfile)" which "can be committed to the project's repository". Jenkins calls this Pipeline-as-code. The delivery process becomes "part of the application to be versioned and reviewed like any other code"jenkins.io, Pipeline. The same page calls committing it "generally considered best practice"..

That's good news for you: a pipeline change is a PR you can review, and its Git history is the audit trail. Here's a realistic Jenkinsfile for a DE repo, orders-etl. Secrets never live in the Jenkinsfile. Credentials "are stored in an encrypted form on the controller" and pipelines handle them "only … via their credential IDs"jenkins.io, Using credentials.. When DevOps says "add the credential and send me the ID", this is what they mean.

3. How the repo and Jenkins are wired

Most teams use a Multibranch Pipeline, one Jenkins job per repo. Jenkins finds every branch that contains a Jenkinsfile and creates a pipeline for each, and with the right plugin it does the same for pull requestsjenkins.io, Branches and Pull Requests. PR support comes from "branch source" plugins (GitHub, Bitbucket, GitLab, Gitea).. Inside the build, two variables tell the pipeline what it's building: BRANCH_NAME (e.g. main) and CHANGE_ID ("such as a pull request number").

On schedules, the docs ask for H (for "hash") "wherever possible". Instead of every job starting at exactly 02:00, H picks a minute derived from the job's name. Each job gets a stable time, and the load is spread outPipeline Syntax, cron..

5. Translating DevOps talk

They say…What's actually happening
"It's stuck in the queue"The build is waiting for a free executor on an agent with the requested label. Nothing is broken yet.
"The agent went offline"A worker machine/container lost its connection to the controller. Builds needing that label wait or fail.
"Re-scan the multibranch"Tell Jenkins to look at the repo again and discover new or deleted branches and PRs
"Add the credential, use the ID"Store the secret on the controller, then reference it with credentials('id')
"Check the console output"The full log of the build: every command each step ran, and its output. (Lesson 3 is about reading it.)
"It's a downstream job"A job "triggered as part of the execution of a separate Pipeline or Job", e.g. tests pass and a deploy job starts

6. Day-to-day stories

Story A: a normal PR on orders-etl

  1. You push branch feature/dedupe and open PR #42.
  2. The webhook fires. Jenkins builds the PR, runs Lint and Test, and skips "Deploy to staging" (it isn't main).
  3. A test fails. The PR shows ✗. You click Details, land on the Jenkins build, open the failing stage's log, and find your bug.
  4. You push a fix, a new build runs automatically, and the PR goes ✓.

Story B: merge day

The PR merges. That's a push to main, so Jenkins builds main, and this time "Deploy to staging" runs, using DWH_TOKEN from the controller's credential store. Nobody pasted a password anywhere.

Story C: "your build has been yellow for an hour"

Your build sits there with no stage started. DevOps: "it's queued, the python agents are all busy." Translation: there are more builds than executors with that label. A fair suggestion you could now make: "Could we add executors or agents for the python label, or shorten our test stage?"

7. Check yourself

Your PR build on orders-etl is green, but "Deploy to staging" shows as skipped. Why?

when { branch 'main' } skips the stage on every other branch and PR. That's by design: PRs get tested, and only merged code gets deployed. (No free executor would leave the whole build queued, not one stage skipped.)

DevOps: "Your build isn't failing, it's just stuck in the queue." What does that mean?

The queue holds builds waiting for an executor slot on an agent with the right label. Without a webhook there would be no build at all, and a syntax error makes the build fail, not wait.

You pushed a new branch with a Jenkinsfile, but no job appears for it. DevOps says "re-scan the multibranch." Why would that help?

A Multibranch Pipeline creates jobs for the branches it discovers. If the webhook was missed (or isn't set up), a scan finds the new branch. The docs note Jenkins won't re-index on its own by default unless periodic scanning is configured.

A teammate wants to paste the warehouse password into the Jenkinsfile "so it's easy." What do you suggest?

Credentials are stored encrypted on the controller and referenced by ID, e.g. credentials('dwh-staging-token'). Base64 is encoding, not encryption. Anyone can decode it, and Git keeps it forever.

Where does sh 'pytest' in your Jenkinsfile actually run?

Steps run on the agent picked by agent { label … }, in a workspace: "a disposable directory on the file system of a Node". Running builds on the controller is discouraged for security reasons.

Last month someone changed the pipeline and deploys broke. You want to know who changed what, and when. Where do you look?

That's the point of pipeline-as-code: the docs list an "audit trail for the Pipeline" as a benefit. git log -p Jenkinsfile shows every change and its author. Workspaces are disposable.

A nightly job uses cron('H 2 * * *'). What does the H do?

H is a hash of the job name, so it's stable for that job, not random each night. It runs once between 02:00 and 02:59, spreading jobs out so they don't all hit the agents at 02:00.
