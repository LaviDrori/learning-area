Reading Our Real Jenkinsfile

The skeleton of the pipeline that moves a Tableau workbook into Git. ~25 minutes.

Your win today: open the real pipeline (the DataPlatformTableauVersion one) and say, for every top-level block, what it sets up, where it runs and what happens if it goes wrong. Lesson 1's generic orders-etl file was a sketch. From here on, this file is the running example.

0. Warm-up: guess first

This pipeline has no cron and no when { branch … }. It has six parameters. How is it most likely started?

Parameters are inputs for a specific run (which workbook, which ticket, which folder). A timer or a push has nobody to supply them. The comments in the file mention a "Harmony workflow" passing the folder, so a Harmony request most likely triggers it. That last part is my inference from the comments, so confirm it with DevOps. The trigger itself is not in this file.

1. What this pipeline is for

In plain words: someone files a Harmony ticket asking to version a Tableau workbook. The pipeline pulls a Docker image that contains the team's Python tool, runs it to download the workbook from Tableau, commits it to GitHub through an auto-merged PR, then runs a final action (copy by default). If the final action fails, it reverts the commit. Harmony is told the outcome either way.

Notice the file mixes two styles. The code inside pipeline { … } is Declarative (structured, like Lesson 1). 3. Three things this file teaches that Lesson 1 didn't

  • It checks out its own code. skipDefaultCheckout true stops Jenkins from putting the repo in the workspace up front. The pipeline needs a different repo (the one it commits workbooks to), so it checks that out itself in stage 3, using a GitHub App credential.
  • One build at a time. disableConcurrentBuilds() makes a second trigger wait in the queue until the running build ends. Two runs would otherwise fight over the same main branch and the same Docker container name.
  • State is passed through env. Each stage records env.CURRENT_STAGE_NAME, and later stages set env.GIT_PUSH_SUCCEEDED. The post { failure } block reads them to tell Harmony where it broke. Plain Groovy variables like deploymentOccurred work too, but env is the safer way to share between stages.
Finding worth raising with DevOps. Two lines in environment hold a real webhook URL and a real bearer token as plain text. The file's own TODO says "move to Jenkins credentials". Anyone who can read the repo (or this file) can post to Harmony as this pipeline. The fix is the Lesson 1 pattern: store them as credentials and read them with credentials('id'). Because the token has been copied out of Git into other places, it should also be rotated. This is exactly the "safer deploys" suggestion your mission asks for.

4. Check yourself

Someone triggers the build and leaves REPORT_FOLDER empty. When does it fail?

Preparation checks REPORT_FOLDER first and calls error(…). That's fail fast: don't waste a Docker pull on a run that can't finish. It also sets HARMONY_NOTIFY_* so the failure message explains why.

Two tickets trigger this job within the same minute. What happens to the second build?

disableConcurrentBuilds() allows one run at a time. The second sits in the queue (the "stuck in the queue" of Lesson 1, but by design). Quick Harmony requests can therefore look slow.

Which lines in the environment block are real secrets sitting in Git?

A credential ID is only a name; the secret stays encrypted on the controller. The bearer token is the secret itself, in plain text. applicationName and the registry host are ordinary config.

The build page says "Waiting for next available executor". The file names the label twice (node(…) at the top, agent { label … } in the pipeline). What does that tell you?

Both use the same label, so setup and stages run on machines from the same pool. If that pool is offline or full, nothing starts. That's an infra cause, not a code bug, and it's the first thing to check on a build that never begins.

A build fails in the middle. Where does the pipeline decide what message Harmony receives?

post { failure } runs after any failed stage. handleGenericFailure() (defined at the bottom of the file) reads env.HARMONY_NOTIFY_ADDITIONAL_INFO or builds a default from CURRENT_STAGE_NAME. That's why every stage sets CURRENT_STAGE_NAME first.

Why are all six parameters declared as string, even ACTION, which only has a few valid values?

Jenkins also has choice, booleanParam and more. With string, a typo in ACTION only fails when the container runs. A choice list would reject it up front. That's a small, concrete suggestion you could make.
