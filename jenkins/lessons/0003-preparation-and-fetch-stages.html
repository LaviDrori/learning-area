Preparation and Fetch: the First Two Stages

Validate, pull an image, run a container, check its exit code. ~25 minutes.

Your win today: read stages 1 and 2 of the real pipeline line by line, and when a build is red, say from the stage and the exit code whether the cause is the input (what was typed into the trigger), the tool (the team's Python code) or the infra (Docker, registry, agents). This is mission goal 3: "open a failed build and tell whether it's my code, the data, or the pipeline."
Same rules as Lesson 2. The excerpts are the real stages, lightly condensed, with secrets, hostnames and internal names replaced by <placeholders>. Line numbers are the excerpt's own.

0. Warm-up: guess first

A step reads sh(script: 'docker rm -f myapp', returnStatus: true). The command fails because no such container exists. What happens to the build?

By default a failing sh "will cause the step to fail with an exception". With returnStatus: true, "the return value of the step will instead be the status code"jenkins.io, sh step.. The pipeline gets a number back and decides what to do. This pattern is all over the file.

3. Stage 2: Fetch Workbook from Tableau

Three Docker flags need explaining first, all from the docker run reference: --name gives the container a fixed name. -e VAR=value sets an environment variable inside it. -v host:container bind-mounts a host folder into it. Anything written after the image name (IMAGE [COMMAND] [ARG...]) is not for Docker: it's the command and arguments for the container.

Lines 15 to 17 are worth a second look: they hold two real suggestions you could make.

4. What the exit code tells you

Line 20 compares an exit code to zero. Where does the number come from? The Docker docs: 125 means "the error is with Docker daemon itself", 126 "the specified contained command can't be invoked", 127 "the contained command can't be found", and "any exit code other than 125, 126, and 127 represent the exit code of the provided container command"Docker docs, Exit status.. That gives you a triage table:

You see in the console…Likely causeWhose problem

Exact message wording differs by Docker version; learn the pattern (which stage, which exit code), not the strings.

5. Two suggestions this code earns you

1. The token is pasted into the command. Line 15 of the Fetch excerpt writes --token ${TOKEN} inside a double-quoted Groovy string. The Jenkins docs say plainly: "Groovy string interpolation should never be used with credentials", and recommend single-quoted sh so the shell expands the variablejenkins.io, Using a Jenkinsfile; credentials-binding step.. Jenkins hides the value as **** in the log, but with interpolation the real token is part of the command that other processes on the agent can list. A fix needs the Python tool to read the token from an environment variable instead of a flag, so it's a DevOps and tool-owner conversation.
2. Free-text parameters flow into a shell command. Lines 16 and 17 wrap WORKBOOK_NAME and REPORT_FOLDER in single quotes, which protects spaces but not a value that itself contains a '. Anyone who can start the build controls those strings. The same docs say to always send "a literal command string" to sh. A cheap guard: validate both against an allowed pattern (like the folder check in Preparation), or make REPORT_FOLDER a choice parameter.

6. Check yourself

Stage 2 fails with "Python script failed during get_file with exit code 125". What's the most useful first reading?

Docker reserves 125, 126 and 127 for its own failures to start the command. A tool failure would normally show another number. So this is a question for DevOps about the image or daemon, not for the tool's owner.

The docker run in the Fetch stage has no --rm. What does that make possible later?

Without --rm ("automatically remove the container … when it exits") the stopped container stays on the agent. Stage 3 runs docker cp against it to pull out output.txt and the workbook. That's why the post block removes it at the end.

Why does stage 2 run docker rm -f <name> || true before docker run --name <name>?

Container names must be unique on a host. A container left by a previous (maybe crashed) build would make docker run --name fail. -f forces removal even if it's still running, and || true means "no such container" isn't an error.

Stage 1 sets env.appVersion = version although version is already a variable. Why?

def version only lives inside Stage 1's script block. Values stored on env survive to later stages. Stage 2 reads env.appVersion ?: params.DOCKER_TAG, with the parameter as a fallback.

A teammate asks for --token ${TOKEN} to stay as it is, because "Jenkins masks it in the log." What's the best reply?

Masking is best-effort and only covers the log. With Groovy interpolation the real value is placed into the command itself. The docs advise a single-quoted sh and letting the shell expand the variable.

The console shows "…get_file with exit code 1…". Where do you look next?

The Python tool's messages (workbook not found, authentication failed…) are printed to the console while docker run executes. The error(…) line only reports the exit code after that. Read upward from the error.
