An Agent Is a Loop

Five separate decisions hide inside every agent you ship. Most of your questions are about just one of them. ~25 minutes, plus an optional 10-minute exercise.

Your win today: split any of your four deployments into five boxes (model, model access, harness, context & tools, hosting), say which box a customer's question is really about, and run the whole agent loop yourself in ~40 lines of Python.

0. Predict first

Guess even if you're unsure. Section 3 answers both.

Your Tableau agent runs in the customer's Kubernetes (deployment #4). A user asks a question. What leaves the customer's network?

Your container is inside, but it calls the Anthropic API on the internet. Every call carries the system prompt (org prompt, field names and descriptions), the conversation so far, and every tool result, which means the rows your VizQL query returned. The answer is written outside, then sent back. Only the hosting moved on-prem.

1. The loop

Anthropic draws a line between two kinds of LLM system:Building effective agents

  • Workflow: "systems where LLMs and tools are orchestrated through predefined code paths". Your code decides the steps.
  • Agent: "systems where LLMs dynamically direct their own processes and tool usage". The model decides the next step.

By that definition, most of your Tableau agent is a workflow. Its main path is a fixed chain of LLM calls (route the question, generate one query with at most one tool round, synthesize the answer), and your code picks every step. Only the multi-step analysis route lets the model run an open tool loop. That isn't a flaw. Anthropic recommends "the simplest solution possible, and only increasing complexity when needed". But you should choose which one you're building on purpose (Lesson 2). An agent loop works like this, and the mechanism is small. You send a request with a list of tools. If the model wants one, the reply ends with stop_reason: "tool_use" and contains a tool_use block: the tool's name and its input. Your code runs it and sends back a tool_result. The docs sum up the whole loop in one line: "while stop_reason == "tool_use", run the tools and continue the conversation." Any other stop reason (end_turn, max_tokens, stop_sequence, refusal) ends it.How tool use works · Tool use overview

2. Five boxes

Every "how should I build my agent" question is really about one of five separate decisions. This split is mine, not a vendor's, but each box maps onto real product categories.

BoxThe question it answersOptions you'll hear
① ModelWhich LLM reasons?Claude Opus / Sonnet / Haiku, Gemini, open-weight models
② Model accessWho serves that model, under which contract, in which region?Anthropic API, Claude on Amazon Bedrock, Claude or Gemini on Google Cloud, a model you serve yourself (vLLM, Ollama)
③ HarnessWho writes the loop, keeps the conversation, handles errors?Your own loop, the SDK's Tool Runner, Claude Agent SDK, Google ADK, LangGraph, managed runtimes
④ Context & toolsWhat does the model see, and what can it do?System prompt, org prompt, field/table metadata, docs in context or via RAG, skills, tools

Within each agent, the cloud and on-prem versions differ in one column only: ⑤. That's good engineering, because you ship one codebase. But it also means "on-prem" in #2 and #4 means "our code runs in your network", not "nothing leaves your network". Box ② is still a cloud API, and each model call carries the prompt, the metadata and the query rows.

Before you promise a customer "nothing leaves", box ② has to move too. The usual options:

  • An open-weight model you serve inside their network (vLLM, Ollama). Then ① changes as well, and so does answer quality (Lesson 8).
  • Claude or Gemini inside the customer's own cloud account (Bedrock in their AWS, or their Google Cloud project). Data still goes to the cloud, but under their contract, IAM and region. On Bedrock, "model providers don't have any access to those accounts… they don't have access to Amazon Bedrock logs or to customer prompts and completions".Bedrock data protection Many security teams accept that. 6. With the customer

"Your agent runs in our cluster, so our data stays here, right?"

Not quite. Point at box ②: "The code runs in your cluster. Each question sends the org prompt, the field metadata and the query results to the model API. If that's a problem, we can serve the model from your own AWS or Google Cloud account, or run an open model inside your network." It's an honest answer, and you've offered them choices.

"Should we move the agent to Vertex?"

Ask "for the model, or for hosting?" before you discuss anything else. If they mean ②, they want Gemini or Claude billed through their Google Cloud account. If they mean ⑤, they want Agent Runtime or Cloud Run to run your container. These are different projects with different costs.

7. Check yourself

The customer's security team asks: "If your agent runs in our Kubernetes, does any of our data leave?" What's the honest answer?

Tool results (the rows) go back to the model in the next request, and that's how it can answer. Box ⑤ moved on-prem; box ② didn't.

You moved the HR agent from Google ADK to calling Gemini through the SDK yourself. Which box changed?

Same Gemini, same Google Cloud access. Only the code that runs the tool loop changed. If the ADK agent was also hosted on Agent Engine and now runs elsewhere, ⑤ changed too.

A user asks about "revenue" and the Tableau agent sums the wrong field. Which box do you look at first?

The model only knows your fields through what you put in its context. If nothing maps "revenue" to a field, it guesses. Anthropic's goal for context: "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." Fix that first; it's cheaper than changing the model. Hosting never changes answers.Effective context engineering

Your loop sends back a tool_result. How does the model know which request it answers?

Every tool_use block has an id, and each result echoes it back as tool_use_id (line 33 of the exercise). The model can ask for two queries with the same tool in one turn, and only the IDs tell them apart.

The customer says "we'll just put it on Vertex". What do you ask back?

Agent Platform (formerly Vertex AI) covers box ② (Gemini, Claude and open models) and boxes ③ + ⑤ (Agent Runtime hosts agents). The other two questions only make sense once you know which box they mean.

Your loop gets stop_reason: "end_turn". What does the code do next?

Only tool_use means "run these and call me again". end_turn means the model is done (lines 46-47). The exercise treats max_tokens and refusal as final too. A production agent should handle them separately; Lesson 2 shows how harnesses do it.
