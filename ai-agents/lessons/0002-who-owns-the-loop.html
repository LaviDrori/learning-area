Who Owns the Loop

Box ③, the harness. Workflow or agent, your own loop or someone else's, and an honest verdict on the harness you built. ~25 minutes, plus two optional exercises.

Your win today: for each part of an agent, say whether it should be a workflow step or an agent loop, list what a harness owns besides the loop, pick a harness from seven options with a reason a customer would accept, and know the two changes that matter most in your Tableau agent's harness.

0. Predict first

Your Tableau agent's query route: classify the question, generate one VDS query (with at most one tool round to look up field values), run it, write the answer. By Anthropic's definition, what is it?

Your code decides every step and their order. The model only fills in each step: which route, which query, which field values to look up. That's a workflow, built from the "routing" and "prompt chaining" patterns. One bounded tool round inside a step doesn't make it an agent. An agent decides how many steps there are.Building effective agents

A customer's security team requires zero data retention (ZDR). Which harness option is ruled out today?

Managed Agents is "not currently eligible for Zero Data Retention or HIPAA" because sessions are stateful: "transcripts persist until you delete them". The Messages API itself is ZDR-eligible. One catch with the Tool Runner, covered in section 5: in SDK 2.x it keeps the conversation on Anthropic's servers by default.Managed Agents overview

1. Workflow or agent, chosen per step

Lesson 1 drew the line: a workflow runs "through predefined code paths", while an agent directs "its own processes and tool usage". The choice is made per step, not once for the whole product. Anthropic's rule: "workflows offer predictability and consistency for well-defined tasks, whereas agents are the better option when flexibility and model-driven decision-making are needed at scale". Agents fit "open-ended problems where it's difficult or impossible to predict the required number of steps", and the price is real: "higher costs, and the potential for compounding errors". So every agent loop needs "stopping conditions (such as a maximum number of iterations)".Building effective agents: workflow patterns are prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer.

Decide each step of a Tableau agent yourself:

"Total sales last month." One number from one query.

The number of steps is known (one query), so a loop adds latency and failure modes for nothing. One call that returns a validated query, then your code runs it.

"Why did churn rise in Q3? Check the likely drivers." You can't know in advance how many queries it takes, and each one depends on the last result.

This is the textbook case for an agent: the path depends on what the data shows. Your analysis route does exactly this, a planner step and then a tool loop capped by a VDS query budget. That's the stopping condition Anthropic asks for.

Deciding whether a question needs an explanation, one query or a multi-step analysis.

Routing "classifies an input and directs it to a specialized followup task". It's one call with a fixed set of answers, the kind of output that structured outputs (section 4) can force into an enum.

Your design passes this test. Router, query route and synthesis are workflow steps; analysis is the one agent loop, and it's bounded. That isn't luck you should apologize for. It's the shape Anthropic recommends. The open questions are about how the harness is built, not its shape.

2. What a harness owns

The 40-line loop from Lesson 1 handled one thing: tool_use → run → repeat. A production harness owns more, and each item is a place where your code, or someone else's, has to be right:

Every stop reasonmax_tokens returns half an answer as if it were whole; refusal returns an empty string. On current models, check stop_reason before reading content.Using the Messages API
Tool errorsA raised exception kills the request. The fix: send it back as a tool_result with is_error: true so the model can correct itself. The Tool Runner does exactly this.Tool runner
LimitsA loop with no round, token or query budget can run up cost on one question. A hard stop with no final turn leaves the user with nothing.

4. Your harness, judged

I read your base provider class, your Claude adapter and your prompt builder. The short version: the loop is better than most, and the provider layer around it costs more than it gives.

Keep: what's right

  • Workflow first, one bounded loop. Exactly the shape from section 1.
  • A careful loop. It caps the rounds and makes a final call with tool_choice: none while tools stay declared, so the history stays valid. It sends thinking blocks back unchanged. Results are matched by id, a tool exception becomes a result, and a dedicated exception stops the loop on a rate limit. The cache breakpoint moves to the last message every round, and real usage is recorded. Most hand-rolled loops get two of these right.
  • A cache-aware prompt. Static rules, then the datasource's fields, sit before the breakpoint. The date, which changes every day, comes after it.

Fix: where it's weak

  • The output contract is a request, not a guarantee. Query generation ends with "Return ONLY valid JSON", then pulls JSON out of free text. The answer's reasoning, assumptions and suggestions come back as text between ---MARKERS---. Structured outputs give "schema-compliant responses through constrained decoding", and they're GA on the Claude API, Bedrock, Google Cloud and Foundry. Your ~50-line prose description of the VDS query shape could be a JSON Schema instead: enum, anyOf and $ref are supported; recursion and numeric bounds aren't.Structured outputs
  • You carry all the model churn. You keep a hand-written table of which models accept temperature and effort, the SDK is pinned at 0.76 (2.3 is current), and effort is smuggled in through extra_body. SDK 2.x sends API version 2026-10-21, which rejects temperature on every model. So the upgrade is a breaking change for that table. Every new model means changes in four adapters.
  • Lowest-common-denominator interface. "Prompt in, dict out" leaves nowhere to pass a schema, so no provider's native structured output gets used. Each adapter also re-implements plain generate, generate-with-history and token counting. One fallback pastes history into the prompt as text. Token counting falls back to len // 4. Tool errors go back as text without is_error.
  • A trap for the next provider. A provider without tool hooks silently answers without tools instead of failing. All four have hooks today, so this isn't a live bug, but provider #5 would degrade with no error.

Is the multi-provider harness worth keeping?

Keep the workflow and the loop. Shrink or replace the provider layer, and decide which on evidence, not on "we might need it".

  1. Count real users of each provider. Your hosted deployment pins Claude. Your eval judge can use another provider, but a judge needs one method (generate text), not a tool loop. If no customer needs a non-Claude model in the tool loop, go Claude-only on the current SDK. "Run it in my cloud" still works through the same SDK's Bedrock, Google Cloud and Foundry clients (box ②, Lesson 7). That covers the portability security teams actually ask about.
  2. If a customer really needs another vendor's model, move the seam up. Instead of "prompt in, dict out", each provider implements "give me a validated Query for this schema" with its own native structured output. Or swap your four adapters for a maintained library such as Pydantic AI, but only after your existing evals show no drop in accuracy.
  3. Don't move to LangGraph or ADK. Neither fixes the two real weaknesses (the output contract and model churn), and your flow is already code-controlled. The one place a graph runtime would earn its keep is the pause for plan approval in analysis. You solved that with conversation history, and at this size that's fine.
  4. Don't use the Agent SDK or Managed Agents here. The Agent SDK is built for agents that work in files and a shell; your tools are HTTP calls to VDS. Managed Agents would put customer data in server-side sessions that aren't ZDR-eligible, and isn't offered on Bedrock. That's the opposite of what your on-prem customers are buying.

The redesign I'd propose for box ③ (Claude-only case): the router returns a structured {"route": enum}; query generation uses messages.parse with a Pydantic model of the VDS query, and strict: true on the field-values tool; analysis keeps your bounded loop, or the Tool Runner with thread=False plus your tools-off final turn; synthesis returns {answer, reasoning, assumptions[], suggestions[3]} instead of text markers. One caution: if you put each datasource's field captions in an enum, every datasource is a new schema. "The first time you use a specific schema, there is additional latency while the grammar compiles" (cached for 24 hours). So keep captions as strings and validate them in code, as your analysis route already does.Structured outputs If you later stream answers to the UI, keep the answer as streamed text and get the metadata from a separate structured call.

The thread surprise. While testing, I found that the 2.x Tool Runner sends a beta header (message-threads-2026-08-12) and only the new messages each turn. The SDK's own docstring says "The loop runs over a message thread by default… Pass thread=False to send the full history every turn." I couldn't find this feature, or how long the server keeps thread data, on the docs' data-retention page (checked 2026-11-01). Until it's documented, use thread=False for any customer whose security team asks where conversations are stored. 6. With the customer

"Why didn't you build it on LangChain, or ADK?"

"Most of the agent is a fixed workflow: classify, generate one query, run it, answer. Only multi-step analysis is a real loop, and it has a hard query budget. That's Anthropic's recommended shape, and it fits in plain code we can read line by line. A framework would add a layer between us and the prompts without adding anything this flow needs. If we ever need long pausable runs, LangGraph is where we'd look."

"Can we run it on Azure OpenAI instead of Claude?"

Ask what the requirement really is. If it's "billing and data in our cloud", Claude through their own AWS (Bedrock) or Google Cloud account usually meets it without switching models (Lesson 7). If it really is "a different model", say what that costs: a provider adapter, plus a full run of your eval set to show answers stay accurate. Price it as a project, not a setting.

7. Check yourself

A tool handler raises an exception in the middle of the loop. What should the harness send back to the model?

The model can recover: pick another field, fix a filter. It needs the error as the result of that call (same tool_use_id), flagged with is_error. The Tool Runner does this automatically; your harness sends the text but not the flag.

The analysis loop reaches its round limit while the model still wants more data. What should happen next?

A forced final turn turns "out of budget" into an answer from the data gathered so far. Keep the tools declared on that call, because the history still holds tool_use blocks. Your harness does this, and the Tool Runner doesn't.

A customer may want another vendor's model in the Tableau agent. Which choice makes that a contained change instead of a rewrite?

The Agent SDK, the Tool Runner and Managed Agents all run Claude only. Portability across vendors needs a seam: yours (best placed at "validated object for this schema") or a maintained one like Pydantic AI or LiteLLM.

Query generation says "Return ONLY valid JSON" and extracts JSON from the reply. What actually guarantees a schema-valid query?

Constrained decoding makes invalid output impossible instead of unlikely. Examples and retries reduce failures, but they cost tokens and latency, and they still can't promise a valid result.

You upgrade the anthropic SDK from 0.76 to 2.3. Which request that worked before can now fail?

SDK 2.x sends anthropic-version: 2026-10-21, and from that version any temperature, top_p or top_k is a 400. Upgrading the SDK also upgrades the API version. Read the migration guide first.

When would the Claude Agent SDK be the right harness for one of your agents?

It's Claude Code as a library: built-in file, shell and web tools, a subprocess per session and state on disk. Great for an agent that edits, runs or inspects files. Overkill for one that makes HTTP calls to VDS.
