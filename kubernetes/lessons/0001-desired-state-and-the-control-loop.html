Desired State & the Control Loop

The one idea everything else in Kubernetes is built on. ~25 minutes.

Your win today: explain, without notes, what happens when you tell Kubernetes "run 3 copies of my app", and which component heals each kind of failure. It's also the mental model behind the classic interview question "what happens when you run kubectl apply?"

1. Start with a container

A container packages an application "along with its runtime dependencies." It runs from a container image, "a ready-to-run software package containing everything needed to run an application".Both quotes: kubernetes.io, Containers. Think of the image as a sealed box: your Python service, the Python interpreter, the libraries. It runs the same on a laptop or a server.

One container on one machine is easy. Now picture 200 services, each needing 3+ copies, spread over 50 machines. Machines die and containers crash at 3am. Someone has to keep all of that running. The overview docs put it this way: "Wouldn't it be easier if this behavior was handled by a system?"See Overview: Why you need Kubernetes. That system is Kubernetes.

2. You declare, Kubernetes converges

You don't tell Kubernetes "start a container on server 7." You tell it what you want to be true, and it works continuously to make it true.

"When you set the temperature, that's telling the thermostat about your desired state. The actual room temperature is the current state. The thermostat acts to bring the current state closer to the desired state."— kubernetes.io, Controllers

In Kubernetes:

  • Desired state lives in an object's spec, e.g. replicas: 3.
  • Current state is what is really running, reported in status.
  • A controller is the thermostat: a loop that never ends. Observe → compare → act → repeat.

This is called reconciliation. It is why Kubernetes is self-healing. Nobody wrote a "recover from crash" script. The loop just notices that have ≠ want and closes the gap. The docs describe Kubernetes as "a set of independent, composable control processes that continuously drive the current state towards the provided desired state".Overview, "What Kubernetes is not".

3. Who does the work: the cluster's anatomy

A cluster has a control plane (the brain: decides) and nodes (the hands: run things).

ComponentRole in the "3 copies" story
kube-apiserverReceives your request. The front door for everyone.
etcdStores replicas: 3, the desired state, durably.
controller-managerIts ReplicaSet controller sees 0 pods but wants 3, so it creates 3 Pod objects.
kube-schedulerSees pods with no node and assigns each one a node.
kubeletOn each node, sees "a pod is assigned to me" and tells the container runtime to start it.

Each role adapted from Kubernetes Components.

Notice: the controller doesn't start containers. As the docs put it, "the Job controller does not run any Pods or containers itself. Instead, the Job controller tells the API server to create or remove Pods." Every component does one small job and hands off through shared state.

And what's a Pod?

"Pods are the smallest deployable units of computing that you can create and manage in Kubernetes." A pod wraps one or more containers that share network and storage. Pods are "relatively ephemeral, disposable entities," so you almost never create one by hand. You create something with a controller behind it, so dead pods get replaced.kubernetes.io, Pods.

5. Retrieval: from memory, not from scrolling up

Scroll so the lesson above is out of sight. Write first, then compare. Effortful recall is what makes this stick.

Map the thermostat analogy onto Kubernetes. What is the "temperature setting", the "room temperature", and the "thermostat"?

Setting = desired state (spec, e.g. replicas: 3, stored in etcd). Room temperature = current state (what's actually running, status). Thermostat = a controller, a never-ending loop that compares the two and acts (via the API server) to close the gap.

You submit replicas: 3 to an empty cluster. Name each component that acts, in order, and what it does.

1. kube-apiserver accepts it and etcd stores it. 2. ReplicaSet controller (in controller-manager) sees 0 ≠ 3 and creates 3 Pod objects. 3. kube-scheduler assigns each unscheduled pod to a node. 4. kubelet on each node sees its pod and has the container runtime start the container.

Quick check

You scale your app from 3 to 5 replicas. What changes first?

You only ever change desired state. Everything else follows as the controllers, scheduler and kubelets each react to the gap.

A container inside pod web-x2k4p crashes. Seconds later, what do you see?

The kubelet restarts the container in place, inside the same pod. A new pod name means the pod itself was replaced, which happens when a pod is deleted or its node dies.

Which component decides which node a new pod runs on?

The scheduler "looks for Pods not yet bound to a node, and assigns each Pod to a suitable node." The kubelet only runs what has already been assigned to it.

Every node is powered off. You scale to 4 replicas. The new pods are…

The controller still creates the pods (desired ≠ current), but the scheduler has nowhere to put them. Pending is one of the most common statuses you'll debug at work. It usually means "can't be scheduled".

Why do you almost never create a bare Pod directly?

No controller owns a bare pod, so no loop holds a desired count for it. If it's deleted or its node dies, it's simply gone. That's why you use workload resources such as Deployments, which is lesson 2.
