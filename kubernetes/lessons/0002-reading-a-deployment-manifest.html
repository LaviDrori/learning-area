Reading a Deployment Manifest

From a YAML file to the pods you see in kubectl get pods. ~25 minutes.

Your win today: look at a Deployment YAML and predict what kubectl get deployments, kubectl get rs and kubectl get pods will show, including what an edit will change. You can also decode any pod name you'll ever see.

0. Warm-up from Lesson 1

Spaced recall: answer before reading on.

Someone deletes one of your pods. Which component creates its replacement?

The ReplicaSet controller sees have 2, want 3 and creates a new Pod object. The kubelet only restarts containers inside pods it already has. Keep the ReplicaSet in mind: it's a big part of today.

A node dies. Which component picks the new node for the replacement pods?

Controllers create the replacement pods with no node assigned. The scheduler then binds each one to a healthy node.

1. A manifest is desired state, written down

In Lesson 1 you changed desired state by clicking buttons. In real life you write it in a YAML file called a manifest and send it to the API server with kubectl apply -f deployment.yaml. Every manifest has the same four top-level fieldskubernetes.io, Objects in Kubernetes, "Required fields".:

FieldOfficial meaning
apiVersion"Which version of the Kubernetes API you're using to create this object"
kind"What kind of object you want to create"
metadata"Data that helps uniquely identify the object, including a name string…"
spec"What state you desire for the object"

You never write status. It is "supplied and updated by the Kubernetes system and its components." That's the thermostat's reading of the room.

3. One manifest, three kinds of objects

You applied one object, but three kinds show up. "The Deployment creates a ReplicaSet that creates three replicated Pods." Each layer is owned by a controller, the same loop idea as Lesson 1:

  • The Deployment controller keeps a ReplicaSet matching your template.
  • The ReplicaSet controller keeps N Pods alive. This is the one that replaced your deleted pod in Lesson 1.

You can read the whole chain from a pod's name alone. "The name of the ReplicaSet is always formatted as [DEPLOYMENT-NAME]-[HASH]. This name will become the basis for the Pods."

nginx-deployment-75675f5897-7ci7o

Deployment name · pod-template-hash (with the Deployment name, this is the ReplicaSet's name) · random pod suffix

The hash isn't random: it comes from "hashing the PodTemplate." Same template, same hash. A changed template gives a new hash, and with it a new ReplicaSetDeployments, "Pod-template-hash label". Its caution: "Do not change this label.".

In practice: in kubectl get pods, pods with the same middle segment belong to the same ReplicaSet, which means the same version of the template. If two different hashes show up for one app, a rollout is in progress or stuck.

4. Labels and selectors: the glue

How does a ReplicaSet know which pods are "its" pods? Not by name, but by labels, which are "key/value pairs that are attached to objects such as Pods." A label selector picks out every object carrying those labels. The docs call it "the core grouping primitive in Kubernetes"kubernetes.io, Labels and Selectors..

So in the manifest, spec.selector says "my pods are the ones labelled app: nginx", and spec.template.metadata.labels stamps app: nginx on every pod it creates. Two hard rules followDeployments, "Selector".:

  • ".spec.selector must match .spec.template.metadata.labels, or it will be rejected by the API."
  • The selector "is immutable after creation." To change it, "you have to delete the Deployment and recreate it."

Hold on to this idea. Soon you'll see that Services find pods for network traffic in exactly the same way, with a label selector.

5. Which edits do what

"A Deployment's rollout is triggered if and only if the Deployment's Pod template (that is, .spec.template) is changed, for example if the labels or container images of the template are updated. Other updates, such as scaling the Deployment, do not trigger a rollout."— Deployments, "Updating a Deployment"
You change…Template changed?What you'll see
replicasNoSame ReplicaSet, its DESIRED count changes. Existing pods keep their names.
image (or anything under template)YesA new ReplicaSet with a new hash scales up while the old one scales to 0. All pods get new names.

7. Predict the cluster

You see pod checkout-5d8f7b9c6d-q2x7m. What's the name of the ReplicaSet that owns it?

ReplicaSet = [DEPLOYMENT-NAME]-[HASH]. The last segment is the random per-pod suffix.

You change replicas: 3 to replicas: 6 and apply. What does kubectl get rs show?

Scaling doesn't touch the template, so the hash stays the same and so does the ReplicaSet. Only its DESIRED count changes. Your 3 existing pods keep their names; 3 new ones join.

You change the image from nginx:1.14.2 to nginx:1.16.1. What happens to the pod names?

The image is inside the template, so the template changes. That gives a new hash, a new ReplicaSet and brand-new pods. Pods aren't updated in place; they're replaced.

A teammate's Deployment has selector.matchLabels: {app: web} but the template has labels: {app: api}. On kubectl apply…

The docs are explicit: the selector "must match .spec.template.metadata.labels, or it will be rejected by the API." Kubernetes catches this mistake before anything runs.

You need to change a live Deployment's selector from app: web to app: shop. What must you do?

The selector is immutable after creation. Deleting the Deployment also deletes its pods by default, which means downtime. That's why the docs say to "plan your selectors up front."

After rolling the image back to nginx:1.14.2, the original ReplicaSet (same old hash) scales back up. Why the same hash?

Same template in, same hash out. So the Deployment finds its old ReplicaSet (kept at 0 pods) and scales it up again. That's why old ReplicaSets are kept around: they make rollbacks cheap. Try it in the simulator if you haven't.
