Services and Ports

How a request finds your container, and the one number that has to be right. ~25 minutes.

Your win today: answer the customer question "What port does it listen on, and how do we expose it?" in one sentence, then find the four port and label mistakes in a manifest a customer sends back.

1. Pod IPs don't last

"Each Pod gets its own IP address", but "Pods are ephemeral resources (you should not expect that an individual Pod is reliable and durable)"kubernetes.io, Service.. Every rollout, crash replacement and scale-down swaps pods, and with them their IPs. So if the customer's frontend, or their Ingress, needs to call forecast-api, which IP does it use?

None of them. It calls a Service: "an abstraction to help you expose groups of Pods over a network". A Service is an object, like a Deployment, and it gives you three stable things:

Stable thingExampleHow
a name in cluster DNSforecast-apiServices get DNS records of the form my-svc.my-namespace.svc.cluster-domain.examplekubernetes.io, DNS for Services and Pods.
a virtual IP, the cluster IP10.96.40.12assigned once when the Service is created, and kept
a selectorapp: forecast-api"The controller for that Service continuously scans for Pods that match its selector, and then makes any necessary updates to the set of EndpointSlices"

An EndpointSlice is the live list of pod IP:port pairs behind a Service. You already predicted (correctly) that a selector matching no pods isn't rejected; the Service simply has an empty list. Now you know where to see that list: kubectl get endpointslices -l kubernetes.io/service-name=forecast-api. "If the ENDPOINTS column is <none>, you should check that the spec.selector field of your Service actually selects for metadata.labels values on your Pods"kubernetes.io, Debug Services..

2. One request, four numbers

Here's where customers' port questions come from. A request to your app passes through a chain, and each hop has its own number:

port vs targetPort. "A Service can map any incoming port to a targetPort. By default and for convenience, the targetPort is set to the same value as the port field"kubernetes.io, Defining a Service.. So a Service with port: 80 and no targetPort sends traffic to port 80 on your pod, where nothing listens. Many customers use 80 by habit, so this is the classic mismatch.

containerPort is a label, not a door. The API reference says: "Not specifying a port here DOES NOT prevent that port from being exposed. Any port which is listening on the default "0.0.0.0" address inside a container will be accessible from the network"Kubernetes API source, Container.ports.. Like EXPOSE, it documents intent. It matters in one case: you can give it a name (say http) and the Service can then say targetPort: http.

The trap on your side: 127.0.0.1. That last sentence said listening on "0.0.0.0". A process bound to 127.0.0.1 (localhost) only accepts connections from inside its own pod. Uvicorn's default is exactly that: "--host… Default: '127.0.0.1'"Uvicorn docs, Settings. Flask's and many dev servers' defaults are also localhost.. On your laptop the browser is on the same machine, so it works. In a pod, every Service call is refused. That's why Lesson 4's CMD has --host 0.0.0.0.

3. Getting in from outside

A Service is only reachable inside the cluster unless its type says otherwise. This is the customer's decision, but you'll hear the words:

They sayWhat it means
ClusterIP (the default)"Exposes the Service on a cluster-internal IP… only reachable from within the cluster."
NodePort"Exposes the Service on each Node's IP at a static port", from a range that defaults to 30000-32767.
LoadBalancer"Exposes the Service externally using an external load balancer", usually one their cloud creates.
Ingress / GatewayNot a Service type. Separate objects that route HTTP(S) by hostname and path (forecast.bank.example/api) to ClusterIP Services, and can "terminate SSL / TLS". The Ingress API is frozen; the project now recommends Gatewaykubernetes.io, Ingress. Types table: Service types..

The most common setup for an HTTP app like yours: a ClusterIP Service, with their Ingress or Gateway in front doing hostnames and TLS. Your app can serve plain HTTP inside the pod. So your part of the answer is short: "It speaks HTTP on port 8000, bound to 0.0.0.0. Point a ClusterIP Service's targetPort at 8000 and route to it from your Ingress or Gateway."

6. Day-to-day stories

Story A: the onboarding questionnaire

Before deploying forecast-api, the bank's platform team sends a form: "Listening port? Protocol? Does the container terminate TLS? Health endpoint?" You answer: 8000, HTTP, no TLS in the container (their Gateway terminates it), health at /health. They create a ClusterIP Service with port: 80, targetPort: 8000 and an HTTPRoute for forecast.bank.example. You never touched a Service, but your answer decided its targetPort.

Story B: "works on my laptop"

A teammate adds a new Docker image for a small admin UI with CMD ["flask", "run"]. On their laptop it works. At the customer, every request through the Service gets connection refused, yet the pods are Running and the EndpointSlice lists them. Endpoints present plus connection refused means something on the right IP isn't listening on the right interface or port. Flask's dev server binds to localhost by default. Adding --host 0.0.0.0 fixes it.

Story C: the 503 after a relabel

The customer's team "tidied up" their labels, changing the Deployment's template to app.kubernetes.io/name: forecast-api. Their Ingress now returns 503. The pods are fine, but kubectl get endpointslices shows <none>: the Service still selects app: forecast-api. A Service doesn't fail when its selector stops matching. It just goes quiet. They update the selector, and traffic is back.

7. A customer asks…

A customer's Service says port: 80, targetPort: 80. Your app listens on 8000. Calls to the Service…

The Service forwards to targetPort and nothing else. It never inspects which ports are open, and a numeric targetPort doesn't consult containerPort. Fix: targetPort: 8000.

The bank says: "Your Service is ClusterIP. How do our users reach it at forecast.bank.example?" Best answer?

Hostname (and path) routing plus TLS is the Ingress/Gateway job, with a ClusterIP Service behind it. A LoadBalancer gives an external IP, not hostname routing. And 443 is outside the default NodePort range of 30000-32767, so the API would reject it.

Your app runs in namespace ml and must call Service model-server (port 8080) in namespace serving. Which URL works?

A bare name is searched in the caller's own namespace first (model-server.ml.svc.cluster.local), which doesn't exist. The DNS docs' example: a pod in test can resolve data.prod or data.prod.svc.cluster.local. Format: service first, then namespace. Put this URL in config, not code (Lesson 6).

Pods are Running, but the customer's Ingress returns 503 and the EndpointSlice shows <none>. What do you compare first?

No endpoints means the selector matched no pods. Port numbers don't affect whether pods are selected; they only matter once traffic is sent. This is Story C.

You delete the whole ports: block (the containerPort) from the Deployment. The Service has targetPort: 8000. Traffic…

"Not specifying a port here DOES NOT prevent that port from being exposed." Only a named targetPort (like http) would break, because there would be no port with that name to look up. Keep containerPort anyway, as documentation.

On your laptop, uvicorn app.main:app works in the browser. In the cluster, every connection to the pod's IP is refused. Why?

Localhost inside a container means "this pod only". Your laptop browser was on the same machine, so it worked there. Add --host 0.0.0.0. Services don't block anything, and a pod's IP is stable for that pod's lifetime.

Appendix: break a Service on your own cluster

~10 minutes on your Docker machine. You need a cluster: in Docker Desktop, open Settings → Kubernetes → Enable Kubernetes. On the EC2 box, install kind and run kind create cluster. You'll run nginx (it listens on port 80), put a Service in front with three different numbers, then break the selector.

Predict: nginx listens on 80, the Service has port 8080, and you run kubectl port-forward service/web 5000:8080. Which address do you open?

port-forward's first number is on your laptop, the second is the Service's port. Kubernetes then maps that to targetPort 80 on a pod. Three numbers, one chain.

Predict: you change the Service's selector to app=nope. What does the EndpointSlice show?

A selector is a query, so matching nothing is valid (you predicted this before Lesson 3). The controller re-evaluates and empties the list. The pods themselves are untouched.

Now run the commands, one at a time. Click a line marked ● to see what every part means.

They're identical in every shell. Copy them from here. port-forward keeps running: open http://localhost:5000, see the nginx welcome page, then press Ctrl+C to continue.

PowerShell

kubectl get nodes
kubectl create deployment web --image=nginx:1.27 --replicas=2
kubectl expose deployment web --port=8080 --target-port=80
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl port-forward service/web 5000:8080
kubectl set selector service web app=nope
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl delete deployment,service web
