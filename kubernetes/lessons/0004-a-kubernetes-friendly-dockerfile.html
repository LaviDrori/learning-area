A Kubernetes-Friendly Dockerfile

Ten lines that decide what a customer's DevOps team will ask you. ~25 minutes.

Your win today: look at a Dockerfile and know, line by line, how it answers four standard customer questions: Where do your logs go? Do you shut down cleanly? Do you run as root? Is anything secret baked in? Then fix a broken one.

0. Warm-up

You re-push a fixed image under the same tag v1.4.0. Nodes that already pulled v1.4.0…

With a real tag, imagePullPolicy defaults to IfNotPresent, and the manifest didn't change, so nothing rolls out (Lesson 3). Every build gets a new tag.

On a healthy node, your app's process crashes. Who restarts the container?

The pod still exists, so the kubelet restarts its container in place. The ReplicaSet only steps in when a whole pod disappears (Lesson 1's three healers). Today's lesson is about what your process does at those start and stop moments.

1. The cluster only sees your image

A customer's cluster can't read your code or ask you how the app behaves. All it gets is the image, and the image does whatever your Dockerfile told it to. So when DevOps asks you a "readiness" question, the answer is usually one line of your Dockerfile:

The customer asks……and the answer lives in
"Where do your logs go?"ENV PYTHONUNBUFFERED=1 + your CMD
"Does it shut down gracefully?"the form of your CMD
"Does it run as root?"USER
"Are there secrets in the image?"ENV, ARG, COPY + .dockerignore
"Is the build reproducible?"FROM (the base image tag)

2. Four habits

① Log to stdout, not to a file

"The easiest and most adopted logging method for containerized applications is writing to standard output and standard error streams." The kubelet stores those streams, and kubectl logs reads them backkubernetes.io, Logging Architecture.. The customer's log collector (Splunk, Datadog, Elastic…) usually picks them up from there as well. If your app writes to /app/server.log instead, kubectl logs shows nothing, and the file disappears when the container does.

The Python catch: when stdout isn't a terminal, which is always the case in a container, Python's stdout "is block-buffered like regular text files". Your print() lines then arrive late and in bursts, and the last ones are lost if the app crashes. The fix is PYTHONUNBUFFERED: "If this is set to a non-empty string it is equivalent to specifying the -u option", which forces the streams to be unbufferedPython docs: sys.stdout, PYTHONUNBUFFERED..

② Stop when asked: exec-form CMD

Pods are stopped all the time: every rollout, scale-down and node drain. To stop one, the kubelet "first sen[ds] a TERM (aka. SIGTERM) signal, with a grace period timeout, to the main process in each container." "The default terminationGracePeriodSeconds setting is 30 seconds." After that, "the container runtime sends SIGKILL"kubernetes.io, Pod Lifecycle: Termination of Pods.. SIGKILL can't be caught, so any request still in progress is cut off.

"The main process" is PID 1 in the container. With the exec form, CMD ["uvicorn", …], uvicorn is PID 1, gets SIGTERM, and shuts down gracefully. With the shell form, CMD uvicorn …, Docker starts your command "as a subcommand of /bin/sh -c, which does not pass signals. This means that the executable will not be the container's PID 1, and will not receive Unix signals"Dockerfile reference, ENTRYPOINT. The same applies to CMD..

③ Run as a non-root, numeric user

Without a USER line, your app runs as whatever the base image says. For python:3.12-slim, that's root. Security-minded customers forbid that. The Kubernetes Pod Security Standards "Restricted" profile requires "Containers must be required to run as non-root users", enforced with runAsNonRoot: true. With that set, "the Kubelet will validate the image at runtime to ensure that it does not run as UID 0 (root) and fail to start the container if it does"Pod API reference, SecurityContext..

The trap: USER appuser (a name) isn't enough. The kubelet can't look names up inside your image, so it refuses with: container has runAsNonRoot and image has non-numeric user (appuser), cannot verify user is non-rootExact message from the kubelet source.. Use a number: USER 10001. One more side effect: a non-root user can't write into root-owned folders like /app, so write temporary files to /tmp (storage gets its own lesson later).

④ Nothing secret or customer-specific in the image

Everyone who can pull your image can read everything in it, including ENV values. Docker's docs are blunt: "Build arguments and environment variables are inappropriate for passing secrets to your build, because they persist in the final image"Docker docs, Build secrets.. A baked-in key also can't differ per customer or be rotated without a rebuild. The pattern instead: the image reads os.environ["OPENAI_API_KEY"] at startup, and the customer's cluster injects the value from a Kubernetes Secret. (Lesson 6 covers how.) A .dockerignore file keeps your local .env and .git out of COPY . ..

Habit ⓪, already covered in Lesson 3, applies to FROM too: python:latest can turn into a new Python version under you. Pin a real tag such as 3.12-slim, or a digest.

5. Day-to-day stories

Story A: the bank's first deploy fails

A bank's platform team deploys forecast-api:v1.4.1. Their namespace enforces the Restricted profile. The pods never start, and kubectl get pods shows CreateContainerConfigError. Their engineer emails you the non-numeric-user message. You change USER appuser to USER 10001, tag v1.4.2, and CI pushes it. They bump the tag in their config repo, and the pods start.

Story B: "every rollout drops requests"

The customer notices that each rollout of forecast-api takes about 30 seconds per pod and some forecasts fail with connection errors. That exact 30 is the giveaway: nothing exits until SIGKILL. Your CMD is in shell form. You switch to exec form, and old pods now exit within seconds of SIGTERM after finishing their in-flight requests.

Story C: "your app has no logs"

Support asks the customer for logs. kubectl logs returns a few lines from an hour ago. Two causes stack up: Python buffering (fixed with PYTHONUNBUFFERED=1) and a logging.FileHandler writing to a file. You switch to a StreamHandler on stdout, and their log collector now has everything.

6. A customer asks…

Your app logs with print(). kubectl logs shows the lines minutes late, in bursts. Most likely cause?

In a container stdout is a pipe, not a terminal, so Python block-buffers it. ENV PYTHONUNBUFFERED=1 makes every line go out immediately.

Their pod spec sets runAsNonRoot: true. Your image ends with USER appuser. What happens?

The check happens on the node when the container starts, not at kubectl apply. A name can't be verified as non-zero, so the kubelet refuses. Fix: USER 10001. The customer could also set runAsUser themselves, but don't make them.

During rollouts, each old pod takes exactly 30 seconds to go away. Your CMD is in shell form. Why?

The grace period is a maximum. A pod is gone as soon as its processes exit. The shell never passes SIGTERM to uvicorn, so the pod waits for SIGKILL at 30s.

A scan finds ENV OPENAI_API_KEY=sk-… in your image. After rotating the key, what's the proper fix?

Docker: build args and env vars "persist in the final image". Base64 is an encoding, not encryption. The image should only read the variable, and the cluster supplies it.

Your Dockerfile has no USER line, and the customer's pod spec says nothing about users. Who runs your app?

runAsUser "Defaults to user specified in image metadata if unspecified." The official Python image doesn't set one, so it's root. Kubernetes doesn't change that unless the pod spec says so.

Appendix: see buffering on your own Docker machine

A 2-minute experiment for habit ①. Each run prints 0 to 4, one number per second. The only difference between the two runs is PYTHONUNBUFFERED. First, predict:

Run 1 has no PYTHONUNBUFFERED. When do its five numbers appear?

With no terminal attached, stdout is a pipe, so Python block-buffers it. The five short lines sit in the buffer until the program exits and flushes it. They aren't lost here because the program exits normally. After a crash they would be.

Now run both commands. Click a line marked ● to see what every part means.

They're identical in every shell. Copy them from here:

PowerShell

docker run --rm python:3.12-slim python -c "import time; [print(i) or time.sleep(1) for i in range(5)]"
docker run --rm -e PYTHONUNBUFFERED=1 python:3.12-slim python -c "import time; [print(i) or time.sleep(1) for i in range(5)]"

CMD

docker run --rm python:3.12-slim python -c "import time; [print(i) or time.sleep(1) for i in range(5)]"
docker run --rm -e PYTHONUNBUFFERED=1 python:3.12-slim python -c "import time; [print(i) or time.sleep(1) for i in range(5)]"

macOS / Linux

docker run --rm python:3.12-slim python -c "import time; [print(i) or time.sleep(1) for i in range(5)]"
docker run --rm -e PYTHONUNBUFFERED=1 python:3.12-slim python -c "import time; [print(i) or time.sleep(1) for i in range(5)]"

Expected: run 1 shows nothing for about 5 seconds, then 0 1 2 3 4 all at once. Run 2 shows one number per second. Bonus: add -t to run 1 (docker run --rm -t …). Docker then attaches a terminal, Python switches to line buffering, and the numbers come out one per second even without the variable. That's why "it works on my machine" in a terminal doesn't prove your logs work in a cluster.
