From git push to a Running Pod

The end-to-end path your app takes into a customer's cluster. ~25 minutes.

Your win today: trace your app from your GitHub repo to a running pod in a customer's cluster, naming every hop. You'll also understand what a customer's DevOps team means by registry, tag, pull secret, GitOps and ImagePullBackOff.

0. Warm-up

You change only the image tag in a Deployment and apply. What does kubectl get rs show?

The image is inside the pod template, so the template changes. That gives a new pod-template-hash and a new ReplicaSet (Lesson 2). Keep this in mind: shipping a new version of your app is a tag change.

Which component actually gets the container running on a node?

The scheduler only picks the node. The kubelet on that node tells the container runtime to start the container, and the runtime has to pull the image first. That pull is today's missing piece.

1. Pods never talk to GitHub

It's a natural guess that a pod "runs your repo". It doesn't. A pod runs a container image, and images live in a container registry: a server that stores images, such as GitHub's ghcr.io, Docker Hub, or a cloud provider's registry. The official docs describe the order: "You typically create a container image of your application and push it to a registry before referring to it in a Pod"kubernetes.io, Images..

2. Walk the pipeline, hop by hop

Here's a realistic day: you ship version v1.4.0 of an AI app, forecast-api, to a customer. Before each next hop, guess what comes next.

3. Image names: read them like an address

ghcr.io/acme/forecast-api:v1.4.0

registry host · image path · tag

  • No registry host? "If you don't specify a registry hostname, Kubernetes assumes that you mean the Docker public registry." So nginx:1.14.2 from Lesson 2 came from Docker Hub.
  • Tags can move; digests can't. "Digests are hashes of the image's content, and are immutable. Tags can be moved to point to different images, but digests are fixed." A digest looks like forecast-api@sha256:45b2….
  • Avoid :latest. "It is harder to track which version of the image is running and more difficult to roll back properly. Instead, specify a meaningful tag such as v1.42.0 and/or a digest."

All three quotes: kubernetes.io, Images.

When does the kubelet re-download an image? That's set by imagePullPolicy. If you don't set it, Kubernetes picks a defaultImages, "Default image pull policy".:

Image referenceDefault policyMeaning
:v1.4.0 (a real tag)IfNotPresentPull only if the node doesn't already have it
:latest or no tagAlwaysCheck the registry every time a container starts
@sha256:… (digest)IfNotPresentContent can't change, so a cached copy is safe
Classic trap: you rebuild and re-push the same tag v1.4.0 with a fix. Nodes that already pulled v1.4.0 may keep running the old image, because IfNotPresent sees it's present. And since the manifest didn't change, no rollout happens either. Rule: every build gets a new tag.

4. Who changes the desired state? Two styles

Hop 4 in the walkthrough, updating the tag in a manifest, can happen in two ways. Customers will tell you which one they use:

Push style ("CI deploys")GitOps style
HowThe CI pipeline runs kubectl apply (or helm upgrade) against the clusterSomeone commits the new tag to a config repo, and a tool inside the cluster syncs it
Source of truthWhatever was last appliedThe config Git repo
Typical toolsGitHub Actions, GitLab CI, JenkinsArgo CD, Flux
Who needs cluster credentialsThe CI systemOnly the in-cluster tool

GitOps is Lesson 1's idea one level up. Argo CD is "a declarative, GitOps continuous delivery tool for Kubernetes" that uses "Git repositories as the source of truth for defining the desired application state." It compares the cluster with Git, and "a deployed application whose live state deviates from the target state is considered OutOfSync"Argo CD docs, overview. Whether it automatically reverts drift depends on its sync settings.. In other words, Git is the thermostat setting and Argo CD is the thermostat.

So, "how do pods connect to GitHub?" They connect in two places, and in neither one does a pod touch GitHub. (1) Your app repo → CI → image in a registry → pulled by the kubelet. (2) With GitOps, a config repo holding manifests → read by Argo CD → applied through the API server. Often these are two different repos, and with customers the config repo is usually theirs.

5. Day-to-day stories

Story A: shipping a bug fix (GitOps customer)

  1. You fix a bug in forecast-api, merge, and tag the commit v1.4.1.
  2. GitHub Actions builds the image and pushes ghcr.io/acme/forecast-api:v1.4.1.
  3. You tell the customer, and their DevOps engineer opens a pull request in their config repo changing v1.4.0 → v1.4.1.
  4. After merge, Argo CD shows OutOfSync, then syncs. The Deployment's template changed, so a new ReplicaSet appears (Lesson 2) and pods are replaced.
  5. If something breaks, they revert the PR. Because the old template returns, so does the old hash and the old ReplicaSet.

Story B: "our cluster can't reach ghcr.io"

Many enterprise clusters can't pull from the public internet. The customer copies (mirrors) your image into their own registry, e.g. registry.customer.internal/vendors/forecast-api:v1.4.1, and points the Deployment's image: at that. What this means for you: never hard-code the image location anywhere they can't change it. Ship versioned images, and make the image an easily overridden value in your manifests.

Story C: "your pods are stuck in ImagePullBackOff"

"The status ImagePullBackOff means that a container could not start because Kubernetes could not pull a container image (for reasons such as invalid image name, or pulling from a private registry without imagePullSecret). The BackOff part indicates that Kubernetes will keep trying to pull the image, with an increasing back-off delay"Images, "ImagePullBackOff". The delay caps at 5 minutes.. Your checklist: Does that exact tag exist in the registry? Is the registry private? If so, does the pod have imagePullSecrets? Can their nodes reach the registry?

6. The actual files

Three small files make up the whole pipeline. Expand them. They're simplified sketches, not copy-paste production files.

Dockerfile (in your app repo): how the image is built 
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Lesson 4 is about making this Kubernetes-friendly: logs, shutdown signals, non-root, no secrets baked in.

.github/workflows/image.yml (in your app repo): CI builds and pushes on each version tag 
name: build-and-push-image
on:
  push:
    tags: ["v*"]                 # runs when you push a tag like v1.4.1
jobs:
  image:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v6
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/acme/forecast-api:${{ github.ref_name }}   # → :v1.4.1

Structure follows GitHub's "Publishing Docker images" guide, which pins each action to an exact commit SHA. Copy versions from there for real use.

deployment.yaml (often in the customer's config repo): where the tag lands 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: forecast-api
spec:
  replicas: 2
  selector:
    matchLabels: { app: forecast-api }
  template:
    metadata:
      labels: { app: forecast-api }
    spec:
      imagePullSecrets:              # credentials for a private registry
      - name: regcred                # a Secret the customer creates
      containers:
      - name: forecast-api
        image: ghcr.io/acme/forecast-api:v1.4.1   # ← the hand-off point
        ports:
        - containerPort: 8000

imagePullSecrets "specifies that Kubernetes should get the credentials from a Secret named regcred". See Pull an Image from a Private Registry.

7. A customer asks…

"Does our cluster need access to your GitHub repo to run the app?"

Nodes pull images from a registry. Only CI reads your app repo. If they use GitOps, their Argo CD reads their config repo, not your code.

The customer mirrored your image into their private registry. New pods now show ImagePullBackOff. Most likely cause?

Pulling from a private registry without credentials is one of the two textbook causes in the docs (the other is a wrong image name or tag). EXPOSE and Service selectors don't affect pulling at all.

"Please don't send us images tagged :latest." Why do they care?

From the docs: with :latest "it is harder to track which version of the image is running and more difficult to roll back properly." Kubernetes will run it; operators just hate it.

You pushed forecast-api:v1.4.2 to the registry an hour ago, but the customer's pods still run v1.4.1. Why?

A registry is passive storage, and pushing to it changes nothing in the cluster. Someone (CI or a config-repo commit) must change image: in the Deployment. That's a template change, so a rollout follows.

The customer uses Argo CD. An engineer changes the Deployment directly with kubectl edit, bypassing Git. What does Argo CD report?

Git is the desired state, so live ≠ target means OutOfSync. Whether Argo CD then reverts the manual change automatically depends on how its sync policy is configured.

A customer wants your image referenced as forecast-api@sha256:… instead of :v1.4.2. What do they gain?

A tag is a movable label; a digest is a hash of the content. Pinning by digest guarantees every node runs byte-for-byte the same image, even if someone re-pushes the tag.
