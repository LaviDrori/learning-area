Git-to-Pod Cheat Sheet

How your code reaches a customer's cluster. Sources: kubernetes.io, Images · Argo CD.

The seven hops

  1. git push a version tag to the app repo (code + Dockerfile)
  2. CI (e.g. GitHub Actions) builds the image
  3. CI pushes it to a registry as host/path:tag
  4. Someone updates image: in the Deployment: CI runs kubectl/helm (push) or a config-repo commit is synced by Argo CD/Flux (GitOps)
  5. API server stores it → template changed → new ReplicaSet → new Pods
  6. Scheduler picks a node → kubelet + runtime pull the image (needs imagePullSecrets if private)
  7. Container runs your CMD → Running

Pods never touch Git. The registry sits between build and run, and the tag links them.

Image reference anatomy

ghcr.io/acme/forecast-api:v1.4.1          # registry host / path : tag
nginx:1.14.2                              # no host → Docker Hub
forecast-api@sha256:45b2…                 # digest: immutable content hash

Rules operators expect

RuleWhy
Never ship :latest to production"harder to track which version of the image is running and more difficult to roll back properly"
Every build gets a new tagRe-pushing an existing tag: no template change, so no rollout, and nodes may keep the cached old image
Digest for strict pinningTags can move; digests can't
Image location must be overridableCustomers often mirror into a private registry

Troubleshooting: ImagePullBackOff

"Kubernetes could not pull a container image (for reasons such as invalid image name, or pulling from a private registry without imagePullSecret)." Retries with increasing delay, up to 5 min.

  1. Does that exact tag exist in the registry? (typos, a tag never pushed)
  2. Is the registry private? Does the pod spec reference imagePullSecrets, and does the Secret exist in the same namespace?
  3. Can the customer's nodes reach the registry (firewall, air-gapped network)?
