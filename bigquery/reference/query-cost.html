Query Cost

What an on-demand query is billed for. Sources: Control costs · Querying partitioned tables · Clustered tables · Pricing.

The formula

billed ≈ (sum of the referenced columns' logical sizes) × (share of partitions not pruned), rounded up to the MB, at least 10 MB per table. $6.25/TiB in the US after 1 TiB/month free. Errors and cache hits are free. The billing project (where the job runs) pays.

Table design

CREATE TABLE `proj.ds.predictions`                 -- backticks: project IDs may contain hyphens
(forecast_date DATE, store_id INT64, product_id INT64, predicted_qty FLOAT64)
PARTITION BY forecast_date                          -- daily by default; skip whole days
CLUSTER BY store_id, product_id                     -- ≤4 cols; most-filtered first; skip blocks
OPTIONS (require_partition_filter = TRUE);          -- no date filter → free error, not full scan
  • Clustering is "generally a good first option" (tables > 64 MB).
  • Add partitioning for strict up-front estimates, partitions averaging ≥ 10 GB, or per-partition long-term storage pricing.

Guards in your app (Python)

client = bigquery.Client(project="forecast-app-prod")              # billing project
cfg = bigquery.QueryJobConfig(dry_run=True, use_query_cache=False)  # estimate, free
client.query(sql, job_config=cfg).total_bytes_processed             # upper bound, bytes
cfg = bigquery.QueryJobConfig(maximum_bytes_billed=50 * 1024**3)    # fail, uncharged, above 50 GB
client.query(sql, job_config=cfg).result()                          # real run; raises if over cap

Same in the CLI: bq query --use_legacy_sql=false --dry_run '…' and --maximum_bytes_billed=….

Catches: the cap checks the estimate, so clustered queries can fail under it, so leave headroom. Dry runs return 0 bytes on row-level-secured tables.

Find expensive queries

SELECT creation_time,
  total_bytes_billed / POW(1024, 3) AS gb_billed,                -- empty under capacity pricing
  LEFT(query, 120) AS query_start
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_USER                 -- your jobs; region must match; 180 days
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)  -- prunes the view
  AND job_type = 'QUERY'
ORDER BY total_bytes_billed DESC LIMIT 5;
