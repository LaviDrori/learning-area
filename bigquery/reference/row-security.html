Row Security

Who sees which HR rows. Sources: Authorized views · Authorized datasets · Row-level security intro · Use row-level security · Best practices.

The setup

  • security.access (gcpUser, employee_id, access_reason): one row per viewer × visible employee × reason (SELF, MANAGER_TREE, HRBP_TREE, PEOPLE_ANALYTICS).
  • Views in hr_views (an authorized dataset) read hr + security; employees read only hr_views.
  • SESSION_USER() = email of whoever's credentials sent the job (agent as user ✓; owner-credential dashboard, scheduled query, service account ✗).

The view

CREATE OR REPLACE VIEW `acme-dw.hr_views.my_people` AS
SELECT e.snapshot_date, e.employee_id, e.full_name,       -- name columns: never e.*, no salary
       e.department, e.manager_id, e.job_level
FROM `acme-dw.hr.employee_snapshot` AS e
WHERE e.employee_id IN (                                  -- IN, not JOIN: no duplicates
  SELECT employee_id FROM `acme-dw.security.access`
  WHERE gcpUser = SESSION_USER());                        -- caller, not view author

Callers filter snapshot_date with a literal date (prunes through the view). No OR next to the SESSION_USER() condition.

"Which data can X see?"

SELECT employee_id, STRING_AGG(access_reason, ', ') AS reasons   -- 2+ reasons = JOIN duplicate
FROM `acme-dw.security.access` WHERE gcpUser = 'dan@acme.com'
GROUP BY employee_id;

SELECT gcpUser, STRING_AGG(access_reason, ', ') AS reasons       -- who can see E13
FROM `acme-dw.security.access` WHERE employee_id = 'E13'
GROUP BY gcpUser;

Plus everyone with direct read on hr (IAM): they bypass the views.

Leaks to check

  • "All current and future views" in an authorized dataset can read the source: an unfiltered debug view leaks to every reader. Drafts elsewhere.
  • Who can create/update views in hr_views decides everyone's filter.
  • Copies lose the filter: agent turns, exports, extracts, scheduled-query outputs.
  • Stale access table after re-orgs: old manager keeps access until the rebuild.
  • Side channels (crafted queries, durations): views are "recommended for flexibility", separate tables "for security".

Row access policies (for tables people read directly)

CREATE ROW ACCESS POLICY maintainers_all ON `acme-dw.agent.turns`      -- create first
GRANT TO ('group:people-analytics@acme.com', 'serviceAccount:…')       -- user: group: serviceAccount: domain:
FILTER USING (TRUE);                                                   -- all rows

CREATE ROW ACCESS POLICY own_turns ON `acme-dw.agent.turns`
GRANT TO ('group:all-employees@acme.com')
FILTER USING (gcpUser = SESSION_USER());                               -- like a WHERE clause
  • Needs table read first → policies → none granted = zero rows → several = union.
  • Dropped by CREATE OR REPLACE TABLE, WRITE_TRUNCATE, bq load --replace. Kept by TRUNCATE TABLE, appends, DML.
  • Filters don't prune; dry run shows 0 bytes; total_bytes_billed empty in INFORMATION_SCHEMA.JOBS.
  • List: console View row access policies or bq ls --row_access_policies project:dataset.table. Remove the last one with DROP ALL ROW ACCESS POLICIES ON ….
  • Filtered users get no write access. Never grant bigquery.filteredDataViewer via IAM.
