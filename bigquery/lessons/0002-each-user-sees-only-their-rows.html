2. How a row access policy works

A policy is attached to one table and has two parts: a grantee list (who it applies to) and a filter that "functions like a WHERE clause".Use row-level security When someone queries the table, BigQuery decides what they see in three steps:

  1. Can they read the table at all? "A user must first have access to a BigQuery table to be able to query it", even if a policy names them. No table access → Access Denied.
  2. Does the table have any policies? None → every row, as before.
  3. Which policies grant them? None → zero rows, silently. One or more → the rows that pass any of their filters (the union). That's why a FILTER USING (TRUE) policy for admins works alongside a narrow one for everyone else.

Grantees are written as user:…, group:…, serviceAccount:…, domain:acme.com or allAuthenticatedUsers. Inside a filter, SESSION_USER() is the querying identity's email, so one policy can serve everyone: "only rows for my stores".

4. What row security does to cost and to your writes

  • Filters don't prune. "Row-level access policy filters don't participate in query pruning on partitioned and clustered tables." own_stores filters on store_id, your first clustering column, but a manager's query still reads every store's blocks unless the dashboard also sends store_id = 12 itself. Google: "Try to avoid making row access policies that filter on clustered and partitioned columns."Best practices
  • The numbers go dark. "BigQuery hides sensitive statistics on all queries against tables with row-level security", including bytes processed and billed. Dry runs "always return 0 bytes" (Lesson 1's catch), and total_bytes_billed in INFORMATION_SCHEMA.JOBS stays empty, so cost reports built on it come out low.Estimate costs
  • Replacing the table drops the policies. CREATE OR REPLACE TABLE and WRITE_TRUNCATE (including bq load --replace) delete them. TRUNCATE TABLE keeps them. With no policies left, everyone with table access sees every row.Intro, "implicit deletion"
  • Readers mustn't write. "Don't grant table write permissions to users who should only see filtered data." A writer could change the rows other users see.

6. The other tool: an authorized view

Sometimes the customer wants managers to see only some columns too, and never touch the table. Then you put a view in a separate dataset and authorize it: "Principals can view the data you share and run queries on it, but they can't access the source dataset directly."Authorized views

Then two grants, both in the console's Sharing menus: on the forecast dataset, authorize the view (the view may read it); on shared_views, give the managers' group BigQuery Data Viewer (they may read the view). The datasets must be in the same region. One catch: if the source table also has row access policies, the view's results are still "filtered according to the underlying source table's row-level access policies", so managers then need a policy too.

8. Day-to-day stories

Story A: the assistant that answered too well

A store manager asks forecast-app's AI assistant "how does my store compare with the others?" Your backend runs as the service account and normally appends WHERE store_id IN (…) to your queries. But the assistant writes its own SQL, and it helpfully leaves the filter out. Every store's numbers reach a manager who shouldn't see them. The fix isn't a better prompt: the assistant's queries run with the user's credentials, so own_stores filters them whatever SQL the model writes.

Story B: the morning everyone saw everything

Your nightly job reloads predictions with WRITE_TRUNCATE. The next morning Bob, who saw zero rows yesterday, sees every store, and the console's row access policies list is empty: the replace deleted both policies. You switch the job to TRUNCATE TABLE then INSERT (or a MERGE, Lesson 6), which keeps them, and add a check that lists the table's policies after each run and alerts when the list is empty.

Story C: "can a manager work out other stores' numbers?"

The customer's security team asks. Your honest answer, from Google's own page: row-level security can leak through side channels such as query duration, which "requires many repeated attempts over a range of key values". BigQuery hides the bytes statistics for that reason. If even that risk is too much, as for an outside partner, use separate tables. Row-level security is for use "within your organization", and filtered users get no write access.Best practices

A row is returned if any policy that grants you lets it through. TRUE lets everything through. The narrower policy can't take rows away.

Your nightly job must replace all of predictions' rows and keep its row access policies. Which keeps them?

CREATE OR REPLACE TABLE and WRITE_TRUNCATE drop the table's policies. "TRUNCATE TABLE does not remove policies."

Your app runs a dry run before each manager's query on predictions. It always prints 0 bytes. Why?

On row-level-secured tables "dry runs always return 0 bytes", to prevent side-channel attacks. Your estimate is blind here, so lean on maximum_bytes_billed and filters the dashboard sends itself.

The customer will share forecasts with an outside supplier, who must not even learn how many rows other suppliers have. Best tool?

Google: separate tables are "a good choice when you need to share data with others and you need to keep data isolated", for "third-party partners and vendors, when the total number of rows must be secret". Row security is for use within your organization.
