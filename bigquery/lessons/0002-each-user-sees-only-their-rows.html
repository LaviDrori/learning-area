Each User Sees Only Their Rows

Authorized views, the access table, SESSION_USER(), and the places HR data slips past the filter. ~25 minutes.

Your win today: answer the People Analytics team's everyday question, "which data can employee X see, and why?", with one query; predict exactly what any employee gets from the views; and find the four lines in a view that leak or duplicate HR rows.

0. Predict first

Guess even if you're unsure. A wrong guess now makes the right answer stick better later.

Shir joined this morning. She can read the views dataset, but tonight's job hasn't added her rows to the access table yet. She asks the agent about her own profile. She gets…

The view keeps rows whose employee_id is in (SELECT … FROM access WHERE gcpUser = SESSION_USER()). No access rows, empty list, empty result. "See yourself" is a row in the access table, not a rule BigQuery knows. Access Denied would mean she can't read the view at all.

Yael is on the People Analytics team and also manages Gil, so the access table has two rows for (Yael, Gil). A view JOINs employees to the access table on employee_id. Yael sees Gil…

A JOIN returns one output row per matching pair. Two access rows, two copies of Gil, and every headcount Yael builds on that view is inflated. Filter with IN (subquery) instead, which only asks "is there a match?". Section 2 shows it.

1. Your setup, named

This is the customer's design, in the words this course uses from now on:

  • Access table, security.access (gcpUser, employee_id, access_reason): one row per (viewer, employee they may see). The four rules become rows: SELF, MANAGER_TREE (everyone under a manager), HRBP_TREE (an HR business partner's population), PEOPLE_ANALYTICS (everyone).
  • Authorized view: "Principals can view the data you share and run queries on it, but they can't access the source dataset directly." Your views live in hr_views; employees get read access there and nowhere else.Authorized views
  • Authorized dataset: instead of authorizing views one by one, hr_views as a whole is allowed to read hr and security. "All current and future views in an authorized dataset have access to the tables in the shared dataset."Authorized datasets Remember "future". It matters in section 4.
  • SESSION_USER() "returns the email address of the user that's running the query": whoever's credentials sent the job. Your agent runs queries as the user, so it's the employee. A dashboard that runs on its owner's credentials, or a service account, would make it that identity instead.Security functions

4. Where HR rows slip past the filter

  • An unfiltered view in the authorized dataset. "All current and future views" in hr_views can read hr. A debug view SELECT * FROM hr.employee_snapshot created there is readable by every employee who can read hr_views. Drafts go in a dataset that isn't authorized.
  • Who may create or change views in hr_views. They decide everyone's filter. Google requires them to have "bigquery.tables.getData on the referenced tables" too, so it's a short list of people who already see all of HR. Keep it short.Authorized datasets
  • Copies of the answer. Rows that leave a view lose its filter. agent.turns holds employees' questions and the HR answers the agent gave them. Anyone who can read that table reads everyone's answers. Story A fixes it.
  • The wrong identity. Anything that queries the views as someone other than the employee: a dashboard on its owner's credentials, a scheduled query, a service account. It sees that identity's rows, and so does everyone it shows them to.
  • A stale access table. After a re-org, the old manager sees the moved employee until the access table is rebuilt.
  • Side channels. Google rates authorized views "Recommended for flexibility", but they "can be vulnerable to carefully crafted queries, query durations, and other types of side-channel attacks."Intro to row-level security, comparison table
Cost side effect. Results of queries that use SESSION_USER() are never cached. Neither are queries on row-level-secured tables. So every dashboard refresh through these views runs, and is billed, again. The cache is per user anyway.Cached results Lesson 1's habits are what keep this cheap: few columns, and a literal snapshot_date filter from the caller.

6. Day-to-day stories

Story A: the agent's memory

The agent's service account writes every turn (who asked, the question, the SQL, the answer) to agent.turns. To show people their history, someone grants all employees read access on the agent dataset. Now Noa can read Dan's question "who on my team is a flight risk?" and the answer. The answers came through Dan's filter; the log has none. One fix that keeps the table where it is: two row access policies on it, the same pattern Google recommends for any table (one full-access policy for maintainers, one filtered policy for everyone else).Best practices for row-level security

Row access policies hide rows in place, so employees query agent.turns directly and each gets only their own turns. Two rules come with them: a person not named in any policy gets zero rows, and replacing the table (CREATE OR REPLACE TABLE, WRITE_TRUNCATE) deletes the policies. The service account must only ever append.Intro to row-level security

Story B: Monday's re-org

Lia moves from Omer's team to Tal's on Monday morning. The access table is rebuilt nightly from the HR system. Until tonight, Omer still sees Lia and Tal doesn't. Nobody broke anything; that's the design. The question for the customer is how fresh access must be: rebuilding right after each HR system load is a scheduling choice, not a security feature.

Story C: "why does Yael's headcount say 9? We have 7 people."

Yael is on People Analytics and manages Gil, so she has two access rows for herself (SELF, PEOPLE_ANALYTICS) and two for Gil. A view that JOINs the access table counts both of them twice. Section 3's query answers it in seconds: group Yael's access rows by employee, and the ones with two reasons are the duplicates. The fix is IN (subquery) in the view, not DISTINCT in every dashboard.

7. A customer asks…

Bob is a contractor, not in the group that can read hr_views. He manages two people, so the access table has rows for him. He queries hr_views.my_people. He gets…

The access table only narrows what a reader of the view gets. It never makes someone a reader. Reading the view needs a grant on hr_views.

An engineer adds hr_views.debug_all, a SELECT * on hr.employee_snapshot with no filter. hr_views is an authorized dataset. Who can read every employee through it?

"All current and future views in an authorized dataset have access to the tables in the shared dataset." No extra step authorizes it; being created there is enough.

Dan refreshes his team dashboard, built on hr_views.my_people, twice in five minutes. Nothing changed. On-demand, the second refresh…

Queries that use non-deterministic functions such as SESSION_USER() aren't cached, and the view puts SESSION_USER() into every query on it.

HR asks: "who can see Lia (E13) through the views, and why?" Fastest correct answer?

Every rule is a row, so section 3's second query lists each viewer and their reasons. Add the IAM list of people who read hr directly for the complete answer.

Employees can read agent.turns and should see only their own turns. It has a gcpUser column. Best fix?

Employees can query the table directly, outside the agent, so the filter must live in BigQuery. A row access policy with FILTER USING (gcpUser = SESSION_USER()) does exactly that, plus a TRUE policy for maintainers.
