1. Three questions before any HR row comes back

Every query passes three checks. The first two are IAM, this lesson. The third is Lesson 2.

  • Gate 1, the job. A query is a job, and a job runs in one project. You need bigquery.jobs.create "on the project from which the query is being run, regardless of where the data is stored." The role that carries it is BigQuery Job User, which "can only be granted on" projects, folders and organizations.Run a query · BigQuery IAM roles
  • That project pays. "The querying project is billed for the query job." The job ID shows it: in <project_id>:<region>.<job_id>, the project is the one billed. Storage is billed to the project that holds the data.Manage jobs
  • Gate 2, the data. You need bigquery.tables.getData "on all tables and views that your query references", carried by BigQuery Data Viewer. A normal view needs it on the tables underneath too; with an authorized view or dataset "you don't need access to the underlying source data." That's why employees only need Data Viewer on hr_views.Run a query

2. Where a grant lives, and where it reaches

A grant (Google calls it a role binding in an allow policy) is three things: a role, a member (user:, group:, serviceAccount:) and the resource it's set on. Resources nest:

organization acme.com              (if the customer has one; maybe folders below)
├─ project acme-dw                 the customer's data; storage billed here
│  ├─ dataset hr                   base HR tables
│  │  └─ table employee_snapshot
│  ├─ dataset security             the access table
│  ├─ dataset hr_views             the authorized dataset
│  └─ dataset agent
│     └─ table turns
└─ project people-agent-prod       the agent; its query jobs run and are billed here
   └─ service account people-agent
  • Grants flow down. "Resources inherit the allow policies of the parent resource." A grant on acme-dw reaches every dataset and table in it, including hr.IAM: resource hierarchy
  • They only add. The effective policy is "the union of the allow policy set at that resource" and "the allow policy inherited from its parent." Nothing you set on hr takes back a project-level grant. To find who can read hr, you look at hr and every level above it.
  • Basic roles are wide. Project Owner, Editor and Viewer get OWNER, WRITER and READER on datasets created in the project by default. Google: "Avoid using basic roles. They predate IAM and grant excessive and uneven access."Basic roles

  2. Past the views: everyone with bigquery.tables.getData on hr.employee_snapshot, from a grant on the table, the hr dataset, the acme-dw project, or a folder or organization above it. The query below lists the first two. It only shows "bindings that are explicitly set" on the object you name, not inherited ones, so add the project's IAM page (BigQuery Admin, Data Viewer/Editor/Owner, basic roles) and ask the customer's org admins about folder and organization grants.OBJECT_PRIVILEGES view
  3. Side doors: anyone who can act as an identity from part 2 (Token Creator on a service account that reads hr), and anyone with bigquery.jobs.listAll on the agent's project, who sees the "full (unredacted) details for all jobs", including the SQL the agent wrote for each employee.Manage jobs

Story: "the agent costs us money, why is it on our bill?"

The customer's finance team sees BigQuery charges on people-agent-prod and none for the agent on acme-dw. That's the design: the agent creates every job in people-agent-prod, so that project pays for the queries, while acme-dw keeps paying for storage. It also means every employee needs Job User on people-agent-prod, and none on acme-dw. Want the costs per team instead? Then the jobs would have to run in per-team projects; Google's multi-tenant guide describes such "compute tier" projects.Multi-tenant workloads And recall Lesson 2: SESSION_USER() queries are never cached, so each agent question is billed in full.

7. A customer asks…

Someone gave Noa Data Viewer on the acme-dw project. HR asks: can a grant on the hr dataset take that access away?

Allow policies only add: the effective policy is the union of the resource's own and every parent's. Remove the project grant itself.

Bob, a contractor with Data Viewer on hr_views, opens the console in acme-dw and gets Access Denied: … bigquery.jobs.create. What's missing?

The error names the permission: he may read the view but not run a job in acme-dw. The source isn't checked for an authorized view, and the access table only filters rows after both gates.

The agent's service account appends turns to agent.turns. The least-privilege data grant for that is…

On the project it could rewrite hr too. Google: create "single-purpose service accounts" and "limit its privileges to reduce the potential harm".Service account best practices

Security wants everyone who can read hr.employee_snapshot. You run OBJECT_PRIVILEGES on the table and on the hr dataset. What's still missing?

OBJECT_PRIVILEGES shows only grants set on the object you name. Inherited ones live on the project's IAM page and above. Access-table rows only matter through the views.

A vendor's support group has Service Account Token Creator on people-agent. What can they read?

Impersonating a service account means acting as it, "to gain the service account's permissions". That includes the maintainers_all policy on agent.turns: every employee's questions and answers.
