1. Two ways to pay

Before talking cost with the customer, ask which pricing model their projects use. BigQuery has two:BigQuery pricing

ModelYou pay forWhat "expensive" means
On-demandbytes processed, per TiBa query that reads a lot
Capacity (editions: Standard, Enterprise, Enterprise Plus)slots (units of compute) per hour, reserved or autoscaleda query that keeps many slots busy, slowing everyone else on the reservation

This lesson uses on-demand, where the rules are crisp. Under capacity, bytes stop being the bill, but reading less is still less work for the customer's slots, so the same habits pay off.

On-demand facts worth knowing by heart (check the pricing page for today's numbers):Pricing · Estimate costs

  • $6.25 per TiB processed (US multi-region), after the first 1 TiB per month free for each billing account.
  • Counted in logical (uncompressed) bytes, not the compressed size on disk.
  • Rounded up to the nearest MB, with a 10 MB minimum per table referenced. A tiny lookup still costs 10 MB.
  • Free: queries that return an error, and queries answered from the query cache.

2. The scan is columns × partitions

"BigQuery stores table data in columnar format, meaning it stores each column separately", so it "can read that column data without reading every field of every row".Storage overview A partitioned table is also split into row slices, here one per day of order_date. A query reads only the slices its WHERE clause lets it reach. Skipping slices is called partition pruning.Partitioned tables

3. What prunes, and what quietly doesn't

Pruning works when BigQuery can tell before reading which partitions might match. Google's list:Querying partitioned tables

Prunes ✓Scans everything ✗
order_date = '2026-10-24'
order_date BETWEEN '2026-10-01' AND '2026-10-31'		EXTRACT(MONTH FROM order_date) = 10 (unsupported function)
DATE(ts) = '2025-03-30', TIMESTAMP_TRUNC(ts, MONTH) >= … (supported functions with constant arguments)ts + INTERVAL 1 DAY > CURRENT_TIMESTAMP() (arithmetic on the column; move it to the other side)
a partition filter AND any other filtera partition filter OR another filter
order_date = (SELECT MAX(run_date) FROM …) (value from a subquery)

"Other functions and complex mathematical operations will require a full table scan." The dry run tells you which one you wrote. To make the mistake impossible, a table can set require_partition_filter = TRUE. Then a query without a usable partition filter fails with "Cannot query over table … without a filter that can be used for partition elimination", and failed queries are free.

4. Clustering: pruning inside a partition

A clustered table keeps rows sorted by up to four columns, stored in blocks. "When a block is pruned, it is not scanned." So a filter on store_id skips blocks of other stores.Clustered tables Three things to know:

  • Order matters. The first clustering column takes precedence. Filtering on product_id alone gets less benefit than filtering on store_id.
  • The estimate can't see it. Which blocks get skipped is only known while the query runs, so the dry run is an upper bound. The real bill is often lower.
  • When to pick which. Google calls clustering "generally a good first option" (tables over 64 MB benefit). Add partitioning when you need a strict estimate before running, when partitions would average at least 10 GB, or for per-partition storage pricing.

Partition and cluster, as the customer's orders does: partitions are cut first, then clustering sorts rows within each one.

6. Cap your app's bill

Your app can ask for an estimate (dry run) and set a hard cap (maximum bytes billed) on every job: "If the number of estimated bytes is beyond the limit, then the query fails without incurring a charge."Control costs · Dry-run sample

Two catches. ① The cap checks the estimate, so on clustered tables a query can fail even though its real bill would have fit. Leave headroom. ② On tables protected by row-level security, "dry runs always return 0 bytes". Your printed estimate goes blind there. That's Lesson 2's topic.

8. Day-to-day stories

Story A: the AI assistant's first bill

forecast-app's assistant turns a user's question into SQL. A store manager pins its answer to a dashboard that refreshes every 15 minutes, and the generated SQL is SELECT * FROM orders with a LIMIT. That's 2.18 TB × 96 runs a day, about $1,300 a day in your billing project. The fix is one line: every job the assistant runs gets maximum_bytes_billed. Above it, the user gets "this question would scan too much, add a date range" instead of a bill.

Story B: the dashboard that forgot the date

The customer's analyst builds a Tableau sheet on your forecast.predictions table, filtering only on store. Because you set require_partition_filter, the sheet errors at once with "without a filter that can be used for partition elimination". They add a date filter, and every refresh now reads a few days of one store's blocks instead of years of history. Your table design taught their dashboard good habits.

Story C: "we're on Enterprise, bytes don't matter"

The customer's platform team says their projects run on an Enterprise edition reservation. Now nobody is billed per byte, total_bytes_billed in their job history is informational only, and the cap in your code stops being a money guard.JOBS view But a full scan still occupies their slots and slows everyone else's queries. So your answer is: "We still prune and select only the columns we need. Here are our jobs' slot times if you want to check."

9. A customer asks…

A dashboard filters EXTRACT(MONTH FROM order_date) = 10 AND EXTRACT(YEAR FROM order_date) = 2026 and scans all three years. Best fix?

EXTRACT(MONTH …) is on the "scans everything" list, and the AND can't rescue it, because neither side is a pruning filter. order_date BETWEEN '2026-10-01' AND '2026-10-31' is a constant range on the partitioning column. LIMIT doesn't shrink the scan, and clustering never shrinks the dry-run estimate, so the dashboard's cost would still look like three years.

Your job has maximum_bytes_billed = 10 GB. On a clustered table, the dry run estimates 14 GB, but block pruning would have made it 6 GB. What happens?

The cap is checked against the estimate, which is an upper bound. "On clustered tables, a query can fail even when actual billed bytes would stay under the limit." Leave headroom, or add a partition filter so the estimate itself shrinks.

The customer's analyst reruns an identical report query five minutes later, and the table hasn't changed. On-demand, the second run costs…

Queries answered from the query cache aren't charged. You can see it per job in the cache_hit column of INFORMATION_SCHEMA.JOBS. Your dry-run code sets use_query_cache=False so the estimate shows the full, uncached cost.

You're designing a new 30 GB events table. Queries mostly filter on user_id over any date range. Best first choice?

Google calls clustering "generally a good first option", and suggests adding partitioning when partitions would average at least 10 GB. Daily slices of this table would be tiny, and integer-range partitioning on an ID gives you no pruning on date-range queries.

Your forecast.predictions table has require_partition_filter = TRUE. An analyst runs SELECT * … WHERE store_id = 42. Result?

store_id is a clustering column, not the partitioning column, so the query has no "filter that can be used for partition elimination" and fails at once. Errors are free. This is Story B.
