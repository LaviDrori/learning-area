The Map of the Platform

Where the data lives, where it's processed, who decides who sees it, and what the meter is counting. ~25 minutes.

Your win today: draw the customer's Databricks platform as four boxes from memory, follow one query through them, and place any phrase from the next meeting ("grant it in UC", "spin up a warehouse", "the DLT pipeline failed", "it's in bronze") on that map.

0. Predict first

Guess even if you're unsure. You'll know both answers by section 3.

The customer says "our orders table is in Databricks". On a classic workspace, where are the table's bytes actually stored?

Classic compute and the "workspace storage bucket" both sit "in your AWS account", the customer's. Tables are Parquet files plus a log, in their object storage. Clusters come and go; the files stay. (A newer serverless workspace can use Databricks-managed default storage instead, so it's worth asking which kind they have.)High-level architecture

A SQL warehouse sits idle all afternoon and nobody runs a single query on it. What does that afternoon cost?

"Idle SQL warehouses continue to accumulate DBU and cloud instance charges until they are stopped." Databricks bills compute time, not bytes read. That's the big switch from BigQuery on-demand. The guard is auto stop: stop after N idle minutes.Configure a SQL warehouse

1. Four boxes

In BigQuery you never see storage or compute. Google runs both, and you only see projects, datasets and jobs. Databricks splits them apart, and part of it runs in the customer's cloud account. Databricks' own words:High-level architecture

  • Control plane: "the backend services that Databricks manages in your Databricks account". The web UI, the notebooks and SQL editor, the job scheduler, and Unity Catalog live here.
  • Compute plane: "where your data is processed". It comes in two kinds:
    • Classic compute is "created within each workspace's virtual network in the customer's AWS account".
    • Serverless compute runs "in a serverless compute plane in your Databricks account".
  • Storage: the customer's cloud object storage (S3, Azure storage, GCS). Tables live there as files.

Above the boxes sits the account, "the top-level construct that you use to manage Databricks across your organization": identity, billing, and the list of workspaces. A workspace is "the collaboration environment where users run compute workloads". It's what the customer means by "our Databricks", often one each for dev and prod.High-level architecture

2. Unity Catalog: the names and the permissions

Unity Catalog (everyone says "UC") is "an account-level metastore that registers metadata about data, AI, and permissions". One metastore serves every workspace in a region, so a table and its grants look the same from dev and prod.Databricks components · Unity Catalog Every object has a three-part name, which you already know from BigQuery:

BigQueryDatabricksExample
projectcatalogacme
datasetschemaacme.sales
table / viewtable / view / volume / function / modelacme.sales.orders

The project→catalog, dataset→schema mapping is Databricks' own, from their BigQuery migration guide. One difference: a BigQuery project also holds billing and jobs. A catalog is only a container for names and grants.

Three more words you'll hear:

  • Managed vs external table. Managed: "Unity Catalog handles both governance and the underlying file storage lifecycle". It's "the default and recommended table type", and dropping one deletes its files after a recovery window (7 days by default). External: "Unity Catalog handles governance only". The files sit at a path someone else owns and survive a DROP.Managed tables
  • Volume. "Governance over non-tabular datasets": CSVs, images, PDFs, model files, at paths like /Volumes/acme/sales/raw_files/….Volumes
  • hive_metastore. The old, per-workspace catalog from before UC: "a legacy feature". If the customer still has tables there, they're mid-migration, and those tables don't get UC's grants, lineage or audit.Hive metastore

Grants to users, groups and service principals, lineage ("how data and AI assets flow and connect"), and an audit log of "all data access" all live in UC. When someone says "grant it in UC", this is the box they mean. Per-user rows and masked columns live here too (Lesson 3).

3. Compute: what the meter counts

Databricks bills in DBUs (Databricks Units): "units of processing capability per hour based on VM instance type", charged "per second" while compute is running.Components · Pricing Who sends the bill depends on where the compute runs:

  • Classic: "DBUs plus virtual machine, disk, and associated network costs". That's two bills: one from Databricks, one from the customer's cloud provider.
  • Serverless: "the DBU cost already includes the virtual machine costs".Cost optimization

4. Delta: what a "table" is on disk

"Delta Lake is the default format for all operations on Databricks." It "extends Parquet data files with a file-based transaction log for ACID transactions". A table is a folder of Parquet files plus a log of JSON commits that says which files make up each version.Delta Lake Because old versions stay in the log, you can read the table as it was: time travel, 7 days back by default (BigQuery's default window is also 7 days).Table history New tables use liquid clustering, which "replaces table partitioning and ZORDER".Liquid clustering

7. In the meeting

"Why is the Databricks bill up 30%?"

You now know the first question to ask: which compute? The usual suspects are an all-purpose cluster nobody turns off, a warehouse with auto stop set high or disabled, or a nightly job running on all-purpose compute instead of jobs compute. Bytes scanned, BigQuery's first suspect, isn't the bill here. Lesson 2 is about this.

"Can your app read the gold tables?"

Two separate things have to be true. ① UC must grant your app's identity (a service principal) SELECT on those tables. ② Your app needs compute to run SQL on, usually a SQL warehouse it has permission to use. In BigQuery, that second part was "which project runs the job". Here, it's "which warehouse".

8. Check yourself

In the meeting: "Just grant the analysts SELECT on the gold schema in UC." Which box does that touch?

Grants are UC metadata, stored in the account-level metastore, which belongs to the control plane. Nobody touches bucket policies for this, and a warehouse's permissions only control who may use that compute, not which tables they can read.

A data engineer says "the DLT pipeline failed last night". What's DLT called now?

"The product formerly known as Delta Live Tables (DLT) has been updated to Lakeflow pipelines." You declare the tables you want, and the pipeline works out how to build and refresh them. Lakeflow Jobs is the scheduler that often triggers such a pipeline, which is why people mix them up.

In BigQuery you query acme-dw.sales.orders. On Databricks the same table is acme.sales.orders. What is acme?

catalog.schema.table. The first part is a catalog, Databricks' equivalent of a BigQuery project as a name container. Workspaces aren't part of a table's name: the same UC table is visible from every workspace attached to the metastore.

The platform team says "we still have some tables in hive_metastore". What are they telling you?

"The per-workspace Hive metastore is a legacy feature." Those tables live outside UC, so they miss its grants, lineage and audit, and Databricks recommends migrating them. A good follow-up question: "Are the tables my app needs already in UC?"

"Someone overwrote the gold table an hour ago." Which Delta feature lets them read the version from before?

The transaction log keeps earlier versions. DESCRIBE HISTORY shows the version numbers, and VERSION AS OF reads one (section 4). By default this reaches back 7 days.

A nightly notebook runs on an all-purpose cluster that stays on all day. What does the cost-minded engineer suggest?

Jobs compute starts for the run and "terminates the cluster when the job is complete", so the meter stops. You pay for compute time, so LIMIT doesn't help the bill, and dropping Delta loses transactions and time travel without saving DBUs.

Appendix: on Sunday (~10 min)

In the customer's workspace. Each step only reads metadata, and the queries need a running SQL warehouse for a few seconds.

  1. Open Catalog in the left sidebar. Write down the catalogs you see. Is there a hive_metastore? Are there schemas named bronze, silver or gold?
  2. Open Compute → SQL warehouses. For each warehouse, note its type (serverless, pro or classic), size, and auto stop setting.
  3. Open the SQL editor, pick a warehouse, and run the queries below, one at a time. Swap acme.sales.orders for any table you find in step 1. Click each line marked ● to see what it does.

Expected: the metastore ID tells you the cloud and region (for example aws:eu-west-1:…). DESCRIBE TABLE EXTENDED shows Type (MANAGED or EXTERNAL), Provider (delta) and Location. Bring what you found, and I'll build Lesson 2 around the customer's real setup.
