Deployment Cheat Sheet

Read any Deployment manifest and its kubectl get output. Source: kubernetes.io, Deployments.

The manifest, annotated

apiVersion: apps/v1            # API group/version
kind: Deployment               # which object (and so which controller)
metadata:
  name: nginx-deployment       # prefix of every ReplicaSet and Pod name
  labels: {app: nginx}         # labels on the Deployment itself (not the selector's target)
spec:                          # ── Deployment's desired state ──
  replicas: 3                  # scaling: no rollout
  selector:                    # which pods are mine. REQUIRED, IMMUTABLE
    matchLabels: {app: nginx}  # must match template labels, or the API rejects it
  template:                    # ── Pod blueprint: any change here = rollout ──
    metadata:
      labels: {app: nginx}     # stamped on every pod (+ pod-template-hash)
    spec:                      # ── each Pod's spec ──
      containers:
      - name: nginx
        image: nginx:1.14.2    # repository:tag
        ports:
        - containerPort: 80    # port the app listens on

Decoding a pod name

nginx-deployment-75675f5897-7ci7o

Deployment name · pod-template-hash · random suffix. ReplicaSet name = first two parts. One app showing two different hashes means a rollout is happening or stuck.

Ownership chain

Deployment (Deployment controller) → ReplicaSet (ReplicaSet controller) → Pods (scheduler + kubelet). Don't manage a ReplicaSet owned by a Deployment.

Handy commands

kubectl apply -f deployment.yaml              # submit desired state
kubectl get deployments / rs / pods           # the three layers
kubectl get pods --show-labels                # see labels incl. hash
kubectl get deployment <name> -o yaml         # full object: spec AND status
